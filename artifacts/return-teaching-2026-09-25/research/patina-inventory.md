## 6. Per-user preference storage
`profiles.help_state` JSONB, added in `supabase/migrations/00146_profiles_help_state.sql`. Shape: `{tours: {<tourId>: {completed, abandoned, atStep, completedAt, abandonedAt}}, featureAnnouncements: {<featureKey>: {dismissedAt}}, marginNotes: {<noteKey>: isoInstant}, firstAuthoredAt}` (margin/firstAuthored subkeys added later by decision 5 / Onboarding Wave 1 L6 — see `packages/help-system/src/persistence/types.ts`).

Wired in the portal via `apps/designer-portal/src/components/document/help/help-state-provider.tsx` (`HelpStateProvider`, mounted in the `(document)` layout).
RLS: `profiles` SELECT is public (directory/search); writes gated by existing `auth.uid() = id` policy from `00013_profiles_table.sql`. Migration comment explicitly requires `help_state` stay "metadata only — no PII beyond per-user UX state" given the public-read posture. **This JSONB blob is the natural place to add a `featuresSeen`/`releasesSeen` sub-key for a return-teaching system** — the write-through/localStorage-fallback/migration machinery already exists and could be extended rather than rebuilt.

## Gaps (what does NOT exist)
1. **No release/version-aware gating.** Nothing ties a designer's `help_state` to a specific app release or feature-ship date except the one hardcoded Desk-Walkthrough ship-date constant. No `releasesSeen` concept, no shipped-feature registry a "what's new" system could iterate.
2. **No PostHog person-property store** for `last_seen`/`releases_seen`/cohort-by-version. `identifyUser` sets only `platform`/`email_domain`/`display_name`/`role`.
3. **No "return to portal" detection.** No last-login timestamp read anywhere in the reviewed surfaces (only `created_at` is used, for fresh-vs-existing signup cohorting in the Desk Walkthrough).
4. **No general "what's new" / changelog content type.** `contentTypes.ts` has `welcomeModal` (first-signin only, explicitly "never feature announcements") and `coachmark`/`FeatureAnnouncementCoachmark` (single feature, developer-triggered per mount) — no content type or component that lists "what shipped since you were last here."
5. **No feature/version manifest.** No file enumerates "features designers should be taught" in order — a return-teaching system would need to build this itself (data + selection logic), the UI/persistence primitives already exist.
6. **No CHANGELOG or release-notes page/email** for the designer portal.
7. **/version route is disconnected from the actual Cloudflare deploy path** — cannot be used to detect "designer hasn't seen release N" without new wiring.
8. Vision boundary (not a code gap, but binding): any new mechanism must stay inside the MarginNote/Coachmark quiet-idiom, one-shot, no-dashboard, no-engagement-metric constraints already established by R83/R94/R97 and VISION S4.
