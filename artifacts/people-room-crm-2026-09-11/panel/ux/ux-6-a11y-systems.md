# AX: Accessibility and systems critic

## A. Accessibility

The room already carries a working accessibility floor. `DocSheet` (`apps/designer-portal/src/components/document/overlays/doc-sheet.tsx:24-45`, `:190-260`) is a mature labelled-dialog contract: trapped focus, Esc/backdrop dismiss, focus restoration, nested-modal awareness (`registerManagedModalDialog`/`topActiveModalDialog`), and a `fallbackFocusRef` for an opener that can unmount mid-sheet. Every new sheet this redesign adds (a compliance-document sheet, an access-grants list, a consent record, an affiliation editor) mounts through `DocSheet` unmodified. The charge's "sheets vs routes" and "focus return" items are solved infrastructure, not new work; the direction should say so explicitly so nobody re-designs an overlay.

Two more primitives already pass the bar and should be the templates for every new state surface. `ConsentChip`'s `dotOnly` variant (`person-bits.tsx:182-192`) pairs a colored dot with `role="img"` and a real `aria-label`: a state conveyed by color still has a name. `role="status"` confirmation lines (`roster-row.tsx:331`, `people-room.tsx:459-460`, `call-sheet.tsx:175`) are the room's one aria-live idiom; every new announcement (consent granted, grant expiring, document lapsed) should print into the existing room-level status region rather than spawning a second live region.

Against that floor, four things will break under the panel's own asks. First, the Directory row is one `<button>` (`person-row.tsx:66-101`) whose accessible name is the DOM-order concatenation of every child's text: name, role badge, relationship line, rolodex marker, consent label. "Seats beneath" is exactly the kind of content that, added as more text inside that same button, becomes an unreadable run-on to a screen reader with no way to tab into an individual seat. The row must split into "open this person" (the button) and a separate seats disclosure, its own `aria-expanded`/`aria-controls` button opening a real nested list of focusable seat rows. Second, `StatusDot` (`person-bits.tsx:206-214`) is `aria-hidden` with zero text alternative: lifecycle state is color-only. Every new state dot (consent, document expiry, access-grant expiry) must ship the `ConsentChip` pattern, not a bare colored circle. Third, `RoleBadge`'s GC and architect tints render body text in raw `--color-dusty-blue` with no `-ink` companion (`person-bits.tsx:59,68`; `globals.css:11-47` shows `-ink` variants for clay/terracotta/golden-hour/sage but none for dusty-blue), landing around 2.8:1 on paper and failing the file's own stated 4.5:1 floor. This tint is about to carry more weight: the CRM model widens kinds to inspector, lender, engineer (CRM-10), and several will likely inherit this exact family. Fourth, `party-profile-sheet.tsx` gates consent-dependent controls with the native `disabled` attribute (lines 610, 704, 762, 873), against the house SPEC's explicit rule that a blocked act stays `aria-disabled`, never `disabled` (SPEC.md §A5); a screen-reader user gets no reason why "Invite to texts" is inert. The systems half below adds several new gates (authority threshold, expired compliance document, missing affiliation); every one of them must render as `aria-disabled` plus `aria-describedby` naming the reason and a `.consequence` sentence above the act, per SPEC §A5-A6, or the new gates will be as silent as the old one.

Two smaller but concrete gaps round this out. The role/trade chip rows render as bare buttons with `aria-pressed` but no wrapping `role="group"`/label (`directory-view.tsx:372-391`), unlike the sibling `ScopeLens` (`scope-lens.tsx:39-40`) and `TradeChipRow`, which do label their group; worth fixing once, since the CRM model adds more chip rows (inspector subtype, company kind). And the roster row's disclosure sets `aria-expanded` without `aria-controls`/`id` (`roster-row.tsx:129-131`, `:165`); a pattern to fix before cloning it for "seats beneath" or a documents list.

## B. Systems

The P1 core maps onto three shapes: extend `studio_contacts` (person, company; it already carries the RLS and the rolodex boundary), extend `project_parties` (the engagement, already project-scoped), and add net-new tables for everything that has no home today (reach channel, contact rule, consent, authority, compliance document, site access card). Access grants stay in their nine-plus existing token tables; unifying them into one table is a rewrite nobody is asking for, and a read-only view is enough.

The identity fix (`people_directory`) is the one genuinely structural move. Today it unions six PKs and counts one row per `project_parties` row per project (G-9/CRM-18), so a GC on two jobs is two directory rows and there is no home for "seats beneath." That view must be rebuilt as one row per `studio_contacts` person (or company), with engagements read separately per identity, not per party row. Everything else in the table below can ship incrementally against the existing shape; this one blocks the room's core visual claim and should be sequenced early, behind a flag, with the six-branch view kept live for anything not yet repointed.

Consent (CRM-4) moves from per-`project_parties`-row to per-(studio, channel value) by creating `studio_channel_consent` keyed `(organization_id, channel_kind, channel_value)`, carrying forward every 00432 evidence column verbatim (`source`, `evidence_text`, `evidence_file`, `disclosure_version`, `recorded_by`, `recorded_at`, `opted_out_at`) plus `origin_project_id` for the "opted out on Lindqvist" provenance line. Backfill takes, per phone/email, the most recent evidence row with `opted_out` always winning (mirrors the existing reduction in `_shared/sms.ts:174-185`). `project_parties.sms_consent_status` becomes a read-only cached mirror during transition; the send gate repoints to the new table, not the party row.

Identity merge is recorded, never silent: a `studio_contact_merges` table (`survivor_id`, `merged_id`, `matched_on` enum[profile\|phone\|email], `merged_by`, `merged_at`) keeps both ids resolvable, per crm-model §4's own rule, via a lookup redirect rather than a delete.

Access grants across the nine-plus token tables become one *read* view, `v_access_grants` (`security_invoker`), `UNION ALL` normalizing each table to `(grant_id, tier, subject_ref, scope_ref, granted_by, granted_at, expires_at, last_used_at, revoked_at, revoke_reason)`. Writes stay in each table's own RPC (`create_field_link`, `mint_trade_agreement_token`, and the rest); they have different mint/revoke shapes, and a big-bang merge is not worth the risk. The view is the one place a person's profile, and a screen reader, can answer "what doors are open to them."

Expiry evaluation reuses the shape Patina already ships for exactly this job: `supabase/migrations/00574_invoice_links.sql:1565-1703` runs an advisory lock, a `job_runs` row per invocation, and `cron.schedule`. A nightly `compliance-document-expiry-sweep` job walks `studio_compliance_documents.expires_on`, writing a lapse state the card, the engagement row, and the picker mini-row all read (D-B's "one fact, three readers"), and gating anything in `blocks` (site access, payment, draw, contract). This satisfies AGENTS.md's rule that scheduled jobs are pg_cron with run history in `job_runs`, by extension rather than invention.

One risk worth flagging before it ships: the site access card (E15) is the first genuinely sensitive text in this room (gate codes, alarm codes). The existing client-visibility mechanism, `show_to_client`, is per-*row* not per-*column* (`00419:61-62`, `00420:373-383`); a naive reuse would let a designer accidentally expose a gate code by marking a party row client-visible. The site access card must sit in a studio-only table with no client RLS branch at all.

## Ranked top 5 things Patina must track that it does not today

1. A compliance document with an expiry (COI, W-9, licence, bond) that blocks a named action, held on the Company. Fixture proof: F-11's COI lapsed 2026-03-31 and nothing in Patina knows.
2. Authority: who may approve money, sign a change order, or hold site access, at what threshold, held on the Role-on-project (engagement). Fixture proof: F-04 decides selections, F-05 signs money over $2,500, and neither fact has a field.
3. A contact rule (forbidden channel, route-through, hours) held on the Person, with a per-job override. Fixture proof: F-15 (Frank Bauer) must never be contacted directly; F-27 (the AHJ) must never be texted.
4. One consent record per studio per channel value, not per project row, held as its own object. Fixture proof: F-12's Okonkwo row reads "Not asked" while his STOP from the 2025 Lindqvist job still governs the same phone.
5. A single person identity with seats beneath it, held on the Person (extended rolodex card), not re-derived per project. Fixture proof: F-07 (Tom Marrow) is a different row on every job and a different row again in the studio-wide head count.

## What would change my mind

1. A specimen showing the seats-beneath disclosure actually nested (not a longer flat row) would tell me whether AX-3's split-button proposal survives real content density; I'd want to see it at 8+ seats before ruling the pattern final.
2. Evidence that the send gate's phone-global reduction (`sms.ts:174-185`) is being kept as a permanent secondary check even after `studio_channel_consent` ships would soften AX-7's urgency; right now nothing says the old reduction gets retired, and two sources of truth is worse than today's single, wrong one.
3. A ruling that the site access card is explicitly out of any client-facing surface, in writing, before AX-12 is implemented; without it I'd want the table's RLS reviewed by whoever owns the client-portal RLS sweep, not assumed correct.
4. A working color pair for `--color-dusty-blue-ink` that some other surface is already shipping would let me downgrade AX-2 from "add a token" to "reuse a token"; worth checking before the direction commits to a new hex.
5. Confirmation that the `people_directory` rebuild (AX-4) is sequenced before, not after, the seats-beneath UI ships. Building the UI against the six-branch view first would bake in the exact per-project-row duplication the redesign is meant to fix.
