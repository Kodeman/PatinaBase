# Sourcing, specification and purchasing — source map

Read-only repository audit: 21 October 2026. Prototype files: `sourcing-views.js` and `sourcing.css`. No live data, API calls, external sends, order releases or payments are performed by these views. Sample makers, products, account terms, prices, correspondence and projects are fictional. Evidence below establishes implementation in this checkout, not availability in a particular deployed environment.

## Current architecture and gates

- The current UI is Document-native. Routes are under `apps/designer-portal/src/app/(document)/`: `/library`, `/library/[id]`, `/doc/[id]/pieces`, `/doc/[id]/spec-book`, `/people`, and the project document. The current checkout contains no `src/app/(portal)` directory. The July route map in `.agents/skills/patina-portal-features/SKILL.md` is historical; do not invent current `/portal/catalog`, `/portal/procurement` or `/portal/vendors` screens from it. Catalog and vendor API routes still exist independently.
- Purchase orders are a Studio book sheet, not a separate legacy procurement route: `components/document/studio-drawer.tsx:710` mounts `OrdersLedger`. Its actual pages are Order register, Weekly orders, Receiving and Vendor accounts (`components/document/orders-ledger.tsx:57–67`). The prototype retains these four pages within the Orders view.
- The project worktable is feature gated: `app/(document)/doc/[id]/page.tsx:1000` reads `useFeatureFlag('worktable')`; composition is conditional at 2491 and 3135. Library reach-in is part of this worktable, not evidence that every deployment exposes that arrangement.
- The ready-to-send implementation exists (`components/document/outbound/ready-to-send-sheet.tsx`); comments identify `outbound-review`, and studio settings explicitly reads this flag at `components/document/account/account-studio-page.tsx:227`. This audit did not verify a deployed flag value. It should be labelled implemented/gated where relevant, not promised globally live.
- Room-image hotspots are a proposed entry point into existing pieces, decisions and maker records. They are not an existing library placement mechanism. Product actions retain **Add to project** and the real specification/ordering distinctions.

All abbreviated source paths below are relative to `apps/designer-portal/src/`.

## Prototype state and safety boundaries

- `state.pinned` and `state.quantities` are shared project selections. Adding the initially unselected lamp changes the room and its totals. It does not silently add that new maker to Northline’s PO.
- Chair specification saves `state.studioFinish`. The last client finish remains visible as previous evidence, even when the studio changes its working specification. Parent guards invalidate current design/financial approval when shared scope changes.
- `state.poDraft` remains distinct from `sourcing.po`. Saving a draft is not release, acceptance, payment, fabrication or shipment.
- The received sample project is **Oak Street Apartment**, with one previously released Fieldwork sofa. Its acknowledgement/receipt/exception are isolated under `sourcing`; they do not mutate Lake Mendota’s approval or finance records.
- User-entered values are HTML-escaped. Forms use native types and explicit labels; COM and damage notes have conditional validation. Dates are sample dates. Raw capture does not fetch its URL.
- The specimen’s dark finish is an illustrative tonal study, not a color-accurate product render. The table, sofa and lamp use labelled outline studies, not invented product photography.
- Spec book deliberately omits freeform studio specification/COM notes, custom briefs, trade cost, margin, maker draft contents and account terms. A shared financial summary is not inserted into it.
