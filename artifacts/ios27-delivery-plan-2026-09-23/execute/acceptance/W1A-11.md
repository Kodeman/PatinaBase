### 2.1 direct-orders: `PatinaUITests/DirectOrdersAcceptanceUITests.swift`

These tests drive W1A-14's `PurchaseComposition.UITestDoubles` under
`--uitesting --uitest-order-sheet`. The doubles script the network, and the machine itself stays
live. The oracle is `OrderHandoff`'s own transitions:

- `checkoutDismissed()` moves `.awaitingPayment → .confirming` and arms the poll (`OrderHandoff.swift:180-185`).
- `startPolling` reaches `.placed` only when `dependencies.poll` returns a settled row, and reaches
  `.unconfirmed` at the 60 s deadline (`:214-238`).

| Test | Script | Asserted | Result |
|---|---|---|---|
| `testReturnFromCheckoutHoldsConfirmingUntilThePollSettles` | poll settles on call 4, about 9 s after Done | Right after Safari's Done, "Confirming payment…" shows and `Placed` does not. 5 s later, after two pending polls, the sheet is **still** confirming, with no `Placed` and no `Unconfirmed`. `Placed` appears only after the settled poll. | pass (19.1 s) |
| `testAPollThatNeverSettlesEndsUnconfirmedNeverPlaced` | poll never settles | Confirming shows on return. At the 60 s deadline `OrderSheet.Unconfirmed` appears with the exact `OrderFailureCopy.unconfirmed` sentence. After that, confirming is gone and `Placed` has **never** appeared. | pass (72.1 s) |
| `OrderSheetUITests` (W1A-14's own, re-run) | settles on call 2 | the injected terms render, and the sheet confirms before it places | pass (12.9 s) |

Both new tests cover the plan's sentence: "the sheet must show its confirming state until the
scripted poll answers, and must show the unconfirmed copy when it never does." A sheet that
celebrated on return would fail both tests at the first `XCTAssertFalse(placed.exists)`.

## 3. Findings (dispositions, not repairs)

**F1: After the unconfirmed copy, the sheet still offers "Continue to payment", and tapping it opens a second order.** Severity: high (money). Confidence: high, from source. It was not exercised in the UI.
In `.unconfirmed`, `OrderHandoff.isWorking` is false (`OrderHandoff.swift:74-79`), and the
primary button's enablement depends only on the terms (`OrderSheetContent.swift:105,119`). The
label is still "Continue to payment" (`OrderSheet.swift:335-338`). `primaryTapped()` falls to
`default:` and calls `handoff.begin(productId:)` (`OrderSheet.swift:340-349`), and
`begin` guards only on `!isWorking` (`OrderHandoff.swift:134-136`). So a tester who **paid**,
but whose webhook is late, reads "We haven't seen this payment yet…" directly above an enabled
button that creates a new `create_direct_order` row and a new Checkout session. This ticket did
not check whether the server de-duplicates. **Disposition:** route to T4 as a repair ticket. The
UI oracle already exists (`testAPollThatNeverSettlesEndsUnconfirmedNeverPlaced` reaches the state).
Commercial review before an external tester group is Kody's anyway (W0-DISPATCH §B-8, restated in
plan §7).

**F2: The signed-in cold launch cannot be judged on an unsigned simulator build.** Severity: low (a coverage gap, not a product defect).
The gate builds with `CODE_SIGNING_ALLOWED=NO`, and the Supabase session store then fails with
`Keychain error -34018` (seen in the run log). The signed-in "cold launch lands on the house"
path, and the widget drawing real rows for a signed-in owner, therefore rest on the physical-device
walk (§4). **Disposition:** covered as an owed walk. No change requested.

**F3: `FirstLaunchUITests` is stale, so `ios-gate.sh ui` cannot be green on `main`.** Severity: medium (gate integrity). Confidence: high.
All 7 cases fail at the Threshold wait (`FirstLaunchTestHelpers.swift:99`,
`FirstLaunchUITests.swift:121,171,181`: "Threshold should appear"). The current root is
auth → onboarding carousel → `HouseFirstRoot` (`ContentView.swift`, `AppCoordinator.derivePhase`),
and it has no Threshold or Walk Invitation screen. This ticket did not change those files, and it
added only new files. So the failures come from `main` as it stands, not from this candidate.
Also present: `PatinaUITests.testExample` and `testLaunchPerformance` are Xcode template stubs.
They pass but prove nothing. **Disposition:** a separate test-debt ticket should either retire or
rewrite `FirstLaunchUITests` against the auth → onboarding path (for example, onto
`Onboarding.SkipButton`). Until then, the `ui` tier's exit code is not a usable signal, and an
acceptance verdict has to name its test cases. Not fixed here: the ticket rule is findings, not
fixes, and the repair is outside W1A-11's acceptance scope.
