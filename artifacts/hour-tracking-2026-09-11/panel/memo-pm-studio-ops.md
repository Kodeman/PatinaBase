# Memo — Studio-Operations Project Manager (PM_STUDIO_OPS)

## 1 · Seat and stance

I have run a 2–6 person interior design studio at the exact moment Vision §2 describes: the owner just hired her first hands and the workload doubled. I optimise for the owner knowing by Friday, without asking anyone, where the week went — per person, per project — and for a new hire who logs without being taught. I distrust anything that needs a training session, and any report that needs a spreadsheet stapled to it afterward.

**Derived answer path — "how many hours did my new hire put on the Okonkwo house this week," today:**
1. Owner opens the Hours ledger (`g h`) — she sees only her own entries (`hours-ledger.tsx:113`).
2. She scopes to the Okonkwo house via the project lens (`?projectId=`) — the query still ANDs her own `user_id` (`hours-ledger.tsx:106-119`), so she now sees only her own hours *on that project*, not her hire's.
3. There is no member picker anywhere in the ledger, no admin portal surface (confirmed zero references), and the one piece of code built for exactly this (`useStudioTimeReport`) has never been wired to a button, link, or route.
4. Even a hand-rolled query against `project_time_entries` filtered by `project_id` and the hire's `user_id` would need a role the owner doesn't have from the UI — but if she *could* run it, RLS would actually let it through via `is_project_team_member` (PM_STUDIO_OPS-3), which is the one piece of good news: the data model is closer to answering this than the UI is.
5. **The honest answer today is: she cannot get this number from the product. She has to walk over and ask him, or ask him to screenshot his own ledger.** That is the exact failure this whole program exists to close, and it is a UI/RLS gap, not a data-model gap — the table already has everything (`user_id`, `project_id`, `duration_minutes`, `billable`, `hourly_rate_cents`/`rated_amount_cents`) needed to answer it once a query and a policy exist.

## 4 · The four views

| View | Where it lives | Who sees it | What it shows | What it is NOT |
|---|---|---|---|---|
| My hours | Existing Hours ledger, default scope, unchanged route (`/desk?book=hours`) | every studio member, own entries only (current behavior, keep as-is) | today/week totals, billable %, per-day entries, inline edit until billed | not a new page; not a timesheet-approval flow |
| A member's hours | Same ledger sheet, a scope-lens control gated to `owner`/`admin` (`member_role`) | owner/admin only — a `member`/`guest` never sees this control | the same week view, re-scoped to the chosen person, across all their projects | not a per-member settings page; not visible to the member being viewed differently than their own "my hours" (same shape, just whose data) |
| A project's hours | Same ledger sheet, existing project lens (`?projectId=`), fixed to stop filtering by caller's own `user_id` for anyone who is a project team member | any project team member (RLS `is_project_team_member` already grants this — PM_STUDIO_OPS-3) or owner/admin | every team member's entries on the project, grouped by person, for the shown week | not a project "dashboard" — it's the same ledger sheet, same week rows, grouped differently |
| The studio's hours | Same ledger sheet, scope lens = "the studio," admin-gated, backed by `studio_hours_rollup` RPC | `owner`/`admin` only | totals by member/project/activity for the period, billable vs. non-billable split | not a new admin-portal route; not a chart; not a persistent badge/status indicator (Vision §6) — a table inside the sheet a person already opens weekly |
