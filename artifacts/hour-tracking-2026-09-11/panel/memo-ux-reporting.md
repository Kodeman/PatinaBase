# Memo — UX_REPORTING (Information designer: ledgers, statements, typographic reporting)

## 1 · Seat and stance

I am the seat that has designed printed timesheets and studio statements — I judge every screen by whether it would still make sense as a page of paper, read once, in ten seconds. I optimise for the four views (my / member / project / studio hours) each resolving to one legible sheet a studio owner could print and hand a bookkeeper. I distrust charts that decorate a number instead of showing the rows that produced it, and any total that cannot be traced back to the entries under it.

## 4 · The four views

| View | Where it lives | Who may open it | What it shows | What it is NOT |
|---|---|---|---|---|
| **My hours** | The existing Hours ledger (`hours-ledger.tsx`), `/desk?book=hours`, unchanged doorways (`⌘K`, `g h`). Default scope on open — no click required, exactly as today. | Any signed-in project team member, for their own rows — unchanged from today (`user_id = auth.uid()` in RLS). | Week view grouped by day; per-entry: project · activity · phase (if any) · duration · rate provenance (role · $/hr, or "rate pending" per finding 6) · billing state chip · amount. Front matter: today + week totals, billable % (minutes-based — rate is near-constant for one person), all-time unbilled balance with "Bill it." Batch-add row, pre-filled to any active project lens. | Not a dashboard tile, not a chart — a week of rows a designer already trusts because it is the same sheet whether they are looking at their own hours or, with a click, someone else's. |
| **A member's hours** | Same Hours ledger sheet — a new **scope lens** control at the top (text act, not a tab: "mine · Priya · this project · the studio", scored-word style per SPEC.md §A5's tertiary act, not a segmented control). Selecting a member re-runs the same query shape with `p_subject := <member>`. | `owner`/`admin` only (`organization_members.member_role`), via `user_is_org_member(auth.uid(), studio_id, 'admin')` asserted server-side in the rollup RPC — never client-enforced alone. A `member`/`guest` never sees this option in the lens; the control itself is absent for them, not disabled-and-visible (nothing to discover by inspecting the DOM). | Identical layout to "my hours," with one addition: the member's name leads each row (finding 4) since the reader is no longer implicitly "me." Grouped by day by default; a "group by" act (day / week / project / activity — text, not a dropdown chrome) re-orders the same rows, never re-fetches a different shape. Totals line: that member's week + billable % + unbilled balance for their rows only. | Not a personnel-performance dashboard — no comparison to other members on the same screen, no ranking, no red/green. One member, one sheet, exactly as if they had opened their own ledger and you were looking over their shoulder. |
| **A project's hours** | Same ledger, lens set to a project (already exists today via `?projectId=` from the Account band — this view already half-works, per counts §3). Extend it to include every team member's entries, not just the viewer's own. | Any `is_project_team_member(project_id)` — the RLS SELECT policy for this already exists today and already returns every entry on the project (00177:129-153, `current-state.md:52`); the UI has simply never asked for anyone else's rows. `internal` (`project_id IS NULL`) entries never appear here — they have no project to be scoped to (finding 5). | Rows across every team member on the project, grouped by member by default (switchable to day/activity via the same group-by act as the member view), each row carrying the member's name. Project total, billable %, unbilled balance, and (if a services-agreement billing authority exists) the read-only role→rate table already shown today (`ProjectAuthorityBandForProject`). | Not a burn-down chart against `project_phases.estimated_hours` until finding 14's reconciliation is done — showing "X of Yh est." here today would print two different definitions of "estimated" depending on which column happened to be populated. |
| **The studio's hours** | Same ledger, lens set to "the studio" — the terminal position of the scope lens, not a separate route (D9: capture in the document, review in the drawer — "the drawer" already means this one sheet). | `owner`/`admin` only, same gate as the member view. `member`/`guest` never see this lens option. | Every entry across every project and every internal (no-project) row, for the shown period, grouped by member by default (switchable to project / day / week / activity). Studio totals: total hours, billable %, billable amount (dollars, per finding 7 — never a minutes-only percentage once rates mix), all-time unbilled balance across the whole studio. An explicit "— internal —" group for `project_id IS NULL` rows, never folded silently into any project's total (finding 5). | Not a dashboard — no sparkline, no per-member bar chart, no red/green utilization target. A studio-wide week is still rows grouped by member with a totals line at the bottom, the same typographic object as "my hours," just with more rows and one more grouping choice. This is the view Vision §6 is most tempted to turn into a dashboard; it must not become one. |

**Rate + amount columns, all four views.** Shown whenever `billable = true` and a rate resolves (finding 6 — never silently blank; an unresolved rate on a billable entry prints "rate pending," not nothing). Hidden entirely — no rate column, no amount column, not even a zero — for `billable = false` rows; those rows show only project/member/activity/duration and the "Non-bill" state chip. A `guest`-role viewer never sees a rate or amount column even on their own billable rows unless their own row is the one being viewed as "mine" (rate visibility on your own logged time is not the same permission as rate visibility on someone else's).
