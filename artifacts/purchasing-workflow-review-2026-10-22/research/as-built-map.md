## A. Status vocabulary and what users see

- **PO header:** database vocabulary is `draft`, `confirmed`, `in_production`, `shipped`, `delivered`, `cancelled` ([`00148_procurement_workspace_v1.sql:50–61`](/Users/kody/Code/patina-merged/supabase/migrations/00148_procurement_workspace_v1.sql#L50)). The Orders view exposes “draft”/“cancelled” and lifecycle-position labels; exact rendering differs between Orders rows and the item-level Document. [`orders-ledger.tsx:647–705`](/Users/kody/Code/patina-merged/apps/designer-portal/src/components/document/orders-ledger.tsx#L647) **[H]**
- **Project FFE item:** project item status is independently rendered from PO status in the FFE section. Its logic maps delivery states, and explicitly notes that `delivered`/`installed` are project-item facts. [`ffe-section.tsx:297–311,1560–1574`](/Users/kody/Code/patina-merged/apps/designer-portal/src/components/document/ffe-section.tsx#L297) **[H]**
- **Receiving inspection:** `clean`, `damaged`, `partial` ([`00150_receiving_and_damage_claims.sql:8`](/Users/kody/Code/patina-merged/supabase/migrations/00150_receiving_and_damage_claims.sql#L8)). These describe an inspection, not a PO lifecycle state. [H]
- **Damage claim:** states include `drafted` and `vendor_notified` ([`00150_receiving_and_damage_claims.sql:79`](/Users/kody/Code/patina-merged/supabase/migrations/00150_receiving_and_damage_claims.sql#L79)); vendor notification is a separate, explicit action. [H]
- **Shipment:** 00704 stores shipment dates and tracking; it is not a carrier-fed enum status. [H]

**Where status can conflict:** a PO’s `shipped`/`delivered` and its project item’s `delivered`/`installed` are separate records, updated by different actions. A PO status can therefore describe the order while the project item reflects receipt/installation progress; the UI does not reduce these entities to one canonical status. The existing code even calls out a past visual mismatch between delivered/installed and “Ordered” styling ([`ffe-section.tsx:297`](/Users/kody/Code/patina-merged/apps/designer-portal/src/components/document/ffe-section.tsx#L297)). [H]

## B. Tracking and EasyPost

**Studio POs:** tracking is manual. 00698 adds `purchase_orders.carrier` and `tracking_number` plus the manual RPC; the migration explicitly says tracking save does not move status ([`00698_po_tracking.sql:11–24,45–76`](/Users/kody/Code/patina-merged/supabase/migrations/00698_po_tracking.sql#L11)). 00704 adds `po_shipments` for multiple partial shipments ([`00704_po_cost_lines_shipments.sql:112–170`](/Users/kody/Code/patina-merged/supabase/migrations/00704_po_cost_lines_shipments.sql#L112)). I found no studio-PO polling or carrier event ingestion in these paths. [H]

**Separate Orders-service fulfillment:** `services/orders` has a carrier abstraction, EasyPost implementation, and mock fallback; these are under the marketplace orders service’s fulfillment module, not the studio’s Supabase `purchase_orders` workflow. See [`carrier.factory.ts:22–64`](/Users/kody/Code/patina-merged/services/orders/src/modules/fulfillment/carriers/carrier.factory.ts#L22), [`easypost.carrier.ts:27–56`](/Users/kody/Code/patina-merged/services/orders/src/modules/fulfillment/carriers/easypost.carrier.ts#L27), and [`fulfillment.service.ts`](/Users/kody/Code/patina-merged/services/orders/src/modules/fulfillment/fulfillment.service.ts). [H]

The webhook endpoint is **not configured as a public EasyPost webhook receiver**: its handler is decorated with `@RequirePermissions(ORDER_PERMISSIONS.ADMIN_ALL)` ([`webhooks.controller.ts:29–46`](/Users/kody/Code/patina-merged/services/orders/src/modules/fulfillment/webhooks.controller.ts#L29)). Its handler contains a TODO for signature validation and the validator is unimplemented ([`webhooks.controller.ts:49–54,150–161`](/Users/kody/Code/patina-merged/services/orders/src/modules/fulfillment/webhooks.controller.ts#L49)). A carrier webhook would not satisfy an admin-permission guard as shown; signature verification is not actually performed. [H]

## C. Destinations and split shipments

- `studio_locations` are studio-wide saved destinations, with a type/category and receiver information; `purchase_orders.ship_to_location_id` links one location to a PO while `ship_to` retains the printed snapshot ([`00697_studio_locations.sql:43,115–127`](/Users/kody/Code/patina-merged/supabase/migrations/00697_studio_locations.sql#L43)). [H]
- A job site or client home can be represented as a saved studio location or a typed PO ship-to, but the data model does **not** make destinations job-owned. The earlier review found that the prior UI hard-coded a studio address; the current location support is a later schema/UI layer. [H]
- A single PO has one ship-to destination; the cited schema has no destination on PO lines. A PO shipment likewise records shipment fields and shipment lines but does not add a separate destination field ([`00704_po_cost_lines_shipments.sql:112–170`](/Users/kody/Code/patina-merged/supabase/migrations/00704_po_cost_lines_shipments.sql#L112)). So I found no basis to say lines on one PO can be routed to different addresses. [H]
- The COM model links a supplying fabric PO to the workroom PO; it does not itself define a multi-destination shipment. [`00702_com_pair_submittals.sql:212,273`](/Users/kody/Code/patina-merged/supabase/migrations/00702_com_pair_submittals.sql#L212). [H]
- Riders/cost lines and partial shipments exist. The shipment entity has tracking, BOL and dates; destination is not a shipment-level attribute in the cited model. [H]

## E. Overview and navigation

The buying surfaces are distributed:

1. **Project Document / FFE section:** project-item status, Order cell, PO and shipment controls, install state.
2. **Orders book:** Orders/ledger for vendor POs; Week for deliveries and shipment movement; Receiving for inspections and claims. See [`orders-ledger.tsx`](/Users/kody/Code/patina-merged/apps/designer-portal/src/components/document/orders-ledger.tsx), [`orders-book-week.tsx`](/Users/kody/Code/patina-merged/apps/designer-portal/src/components/document/orders-book-week.tsx), [`orders-book-receiving.tsx`](/Users/kody/Code/patina-merged/apps/designer-portal/src/components/document/orders-book-receiving.tsx).
3. **Line unfold:** movement tracking, acknowledgment, receiving and claim clock.
4. **Desk/Post:** procurement drafts, exceptions, and notices; not a complete purchase/shipping ledger ([`use-desk-engagements.ts:239,351,432`](/Users/kody/Code/patina-merged/apps/designer-portal/src/hooks/use-desk-engagements.ts#L239)).
5. **People:** studio locations and vendor account configuration; destinations are managed separately from the project’s buying flow.

There is no one job-level screen found that reliably answers “every item, current order state, where it is shipping, which partial shipment it is on, and whether received.” [H]
