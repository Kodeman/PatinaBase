## Wave 1 integration rulings (2026-09-06, after review round 3)

- **R17 · One source of truth per document (backend R1, client R3-2, designer DR22).** Once a proposal carries ≥ 1 parts row, `proposal_service_terms` / `proposal_service_rates` are a projection and only `upsert_agreement_parts` may write them. Mechanism (all three, belt and braces): (a) a BEFORE INSERT/UPDATE/DELETE trigger on both tables refuses when the proposal has parts unless the transaction-local GUC `app.agreement_projection = proposal_id` is set — only `upsert_agreement_parts` sets it (same GUC pattern as `app.commercial_document_id`); (b) `upsert_design_services_draft` raises a typed refusal `agreement_composed` when parts exist, and the flag-off seven-facet room shows it as one plain sentence ("This agreement is composed from parts. Open it in the Contract Room with parts on to change it.") and disables Save; (c) if grep proves no client code writes those two tables directly, `REVOKE INSERT, UPDATE, DELETE ON proposal_service_terms, proposal_service_rates FROM authenticated` (regenerate the ACL seed); if a direct writer exists, keep the grant and rely on (a). SQL test: reviewer probe P16 and P3b must now refuse.
- **R18 · One part per money variant (backend R2, designer DR20).** The DB rule "an agreement carries only one part of each money variant" is right; the Add menu must not offer a second ceiling/retainer/cadence/deposit/rate card, and readiness reports the duplicate as a blocker so Save can never hit 23514 from the room.
- **R19 · Standard parts keep stable keys (backend R3).** The nine standard parts always carry their `patina.*` keys; the composer never re-keys them; prose projection (scope, terms, deliverables, exclusions) reads by those keys, and a custom prose part (`custom.<uuid>`) never projects. Test: a rail-composed agreement projects the same terms row the seven-facet room would.
- **R20 · Money projection by kind + variant is accepted (backend R4, designer DR16).** The build sheet's §6.2 cases 6 and 7 are amended to match; recorded here so the deviation is ruled, not silent.
- **R21 · "Not yet set" survives composition (client R3-1).** The composed homeowner body never prints `$0` or `0%` for an unset money part; it prints today's "Not yet set" and readiness blocks send while any money part the class requires is unset. Empty clause/list parts render nothing, not a naked heading (R3-6). The R4 floor reads only client-visible money parts (R3-3).
- Pre-existing red on main, not this wave's to fix, recorded for the main backlog: `direct_order_attribution_test.sql`; `threshold.spec.ts:221` seed-accumulation drift and `:158` timezone fragility; designer-portal lint (2 errors, byte-identical on origin/main). Backend F-5 (a fourth rate-card refusal) is accepted as the build sheet's omission — keep it.

## Program rules for this build

- Waves ship in order, each to production, each behind a fail-closed PostHog flag: `agreement-parts` (W1), `agreement-library` (W2), `design-build` (W3). Kody creates the flags; features are dark until then (verify `/flags` with a real-browser UA before enabling — memory).
- Flag-off must be byte-identical for the designer and client surfaces in W1 (the seven-facet room renders exactly as today).
- No wave reopens `commercial_document_signatures`' two-party constraint. No wave writes business tables outside definer RPCs.
- Every migration: banner, idempotent, RLS in the same file, explicit grants, `search_path` pinned, extension functions schema-qualified, `generate-legacy-grants.py` re-run when grants change, types regenerated.
- Numbers are provisional until merge; re-check the tip before every integration.
- Gates per patina-verification; full designer-portal jest on a clean checkout is the gate before merge (memory lesson).
- Nothing deploys without the chain: migrations → edge functions (every importer of a touched `_shared` file) → portals via `./infra/deploy-portal.sh <name>` from the main checkout → `wrangler deployments list` bottom row + served-chunk grep + behavior probe.
