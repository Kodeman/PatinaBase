What the panel actually does

A simulated designer panel run against fifteen real vendor pages, harvested live on 29 August. Every number below comes from running the extension's own extractor and its own React tree — not from reading the code and guessing. Kody rules; the rulings sit at the end.

Where we stand

Five things that are true this morning

  • Backend real

    Every object the extension writes already lives on Strata and works: products, product_styles, vendors, proposal_captures, and the three RPCs behind library / inbox / client-decision saves. The plumbing is not the problem.

  • Never published

    There is no Patina Capture in the Chrome Web Store. Tag extension-v0.2.0 went out on 4 August; both CI runs failed — the first on CLI flags, the second with ITEM_NOT_UPDATABLE because a manual dashboard submission was already sitting in draft. Nothing has shipped since.

  • 40% inert

    Roughly two fifths of the panel surface can't be reached or doesn't work: six "coming in a later phase" screens with no dispatcher, an offline queue with no producer, an OCR toggle whose assets were never built, a trade-pricing region that's a placeholder, and ~1,300 lines of components nothing imports. A reviewer clicking around will find some of it.

  • Read, not shown

    Dimensions, materials, colours and finish are extracted and persisted — and then never rendered. RecordRegion.tsx edits three fields. Across the fifteen fixtures the extractor recovered 19 dimension values and 55 material strings that no designer can see or correct before saving.

  • Legal 404

    /privacy and /terms are linked from the signup page and both return 404 — the marketing site that owned them lives in another repo. That is a hard Web Store blocker and a live signup bug.

The five that matter

Pinterest breaks extraction in the audit — probably not in Chrome

The run throws DOMException SyntaxError: unknown pseudo-class selector ':3>*' and returns nothing: no name, no retailer, no fallback. But the throw comes from jsdom's nwsapi selector engine parsing a Pinterest class name, inside a constant, pseudo-class-free selector that native Chrome Element.closest() cannot throw on. Treat it as unlikely to reproduce live — Kody's walk settles it.

What is actionable regardless: images.ts:110 and :114 are the only unguarded .closest() calls in extraction/. Every other module in that directory wraps its selector loop. One page should never be able to abort the whole pass.

src/lib/extraction/images.ts:110 · :114 — img.closest('[class*="carousel"], [class*="slider"], [class*="swipe"]')

DWR says the manufacturer is DWR

The page says Herman Miller — as a text label directly above the title. The extractor reports manufacturer and retailer as the same string, derived from the domain. Manufacturer ≠ retailer is load-bearing for every tear sheet, and it is wrong on DWR, RH, West Elm, Chairish and 1stDibs — five of the fifteen.

extraction-report.json — manufacturer == retailer on all 14 fixtures that returned a result

1stDibs prices in Swiss francs

A New York vintage listing came back 7,843.64 CHF, with zero dimensions (the seller's dimension table is free-form) and zero images. The panel then renders the price behind a hard-coded $ glyph — so Dana sees "$7,843.64" and has no way to know the number isn't dollars.

RecordRegion.tsx:113 — literal "$" · confidence still reported "medium"

RH picks the member price, silently

The page shows "$6,995 MEMBER / $9,995 REGULAR". The extractor takes $6,995 and stamps it high confidence — a $3,000 error presented as certainty. Its width options are in feet (8', 9', 10', 11'), which the inch-shaped dimension parser reads as nothing: 0 of 10.

RH also ships an empty <script id="schema" type="application/ld+json"> — a dead placeholder

A brand's promotional post — no product, no JSON-LD, a login wall over the carousel. The extractor returns name "Instagram", price $1.00, manufacturer "Instagram", and calls it medium confidence. Priya starts half her captures on social; this is the first thing she'll see.

The record region edits three fields

Name, Price, Description. That is the whole form. Dimensions, materials, colours and finish have no row, no input, no badge — they travel from the extractor to the database without ever passing in front of a human.

src/panel/regions/RecordRegion.tsx:95 · :109 · :135

Brand never renders straight out of extraction

There is a Brand row, but it renders only when a vendor object is attached, and draftFromExtraction sets both manufacturer and retailer vendors to null. The extractor's "Design Within Reach" string is dropped on the way into the draft.

It can still arrive later: after EXTRACTION_SUCCESS, an async Supabase vendor match dispatches VENDOR_SET, and the row appears if that lookup finds a match. So the row fills in on vendors already in the database — and never appears at all for an unknown retailer or maker, which is exactly Dana's indie-Shopify and vintage-listing case.

Clicks to save

What each destination costs

Discrete interactions from a populated draft to the terminal screen — one select change, one typed field, one button. "Warm" means chrome.storage.local already holds a project and room from an earlier capture this session.

The finding under the numbers

The app remembers where, but not what. saveSpecBookPlacementContext() persists { projectId, roomId } and nothing else. The route kind — library, project inbox, fill slot, create line — is never written down. FFESlotPicker's routeKind always initialises to assigningExisting ? 'fill_slot' : 'library', and assigningExisting is always false on this surface because RouteCommitRegion never passes a productId. The picker is also a fresh component instance every capture — the draft is nulled on EXTRACTION_START, so the region unmounts and its local state has no survival path by construction.

Every capture reopens on "Library only." Even the one immediately after a fill_slot save into the same room. For Marcus at thirty captures a day that is thirty throwaway dropdown changes, purely because route kind isn't part of what's remembered.

Words on the screen

Five strings to fix before a reviewer reads them

Every user-facing string in onboarding, auth, the commit bar, the terminals, the regions, the overlays and the context menus was read against the brand voice. The banned lexicon is clean — nothing says curated, luxury, elevated, or leads with AI. These five are the real gaps.

  1. "Nothing is read in the background, and nothing leaves your workspace."false

    It leaves. PostHog receives analytics and Supabase receives every save and search. This is the install-time trust promise a privacy-conscious designer will hold Patina to later — and the Web Store reviewer compares this sentence to the data-use disclosure. It needs rewriting, not softening: say plainly that the page is read only when you capture, that saves go to your Patina workspace, and that light usage stats are collected.

    src/tabs/onboarding.tsx:140 — step 2, page-access primer

  2. "Save & fill slot" / "Save & create line"jargon

    "Slot" and "line" are internal FF&E spec-book nouns on the single most load-bearing button in the panel, explained nowhere upstream. A designer who hasn't used the portal's Spec Book has no way to know what either one does.

    src/panel/CommitBar.tsx:146-158

  3. "medium confidence"mechanics

    The extractor's own scoring band, printed raw as though it were a feature. Technology is the silent enabler — this is the algorithm's self-assessment shown to the customer, and section three is exactly why it can't be trusted: "high" on RH's wrong price, "medium" on Instagram's $1.00.

    panel/regions/InsightRegion.tsx:43 · overlays/InsightSheet.tsx:29

  4. "Create a client decision" / a bare "Decision" rowunexplained

    "Decision" is a distinct object in Patina's model, and nothing on this screen or before it says what makes it different from an approval or a proposal. The subtitle assumes the reader already knows.

    overlays/DecisionSheet.tsx:61 · overlays/RecentCapturesSheet.tsx:17

  5. "verified, priced, and routed to the right project"puffery

    Nothing is verified. Extraction is best-effort scraping against pages that fight it — this lane found a wrong currency, a wrong price tier, five wrong manufacturers and a page that returned nothing at all. Numbers and claims in Patina copy have to be true; drop "verified".

    src/tabs/onboarding.tsx:106 — step 0 pitch

Kody's walk

What only a signed-in pass can settle

Everything above came from jsdom and React Testing Library — no Chrome, no login, no built extension. artifacts/capture-launch-2026-08-29/walk-sheet.md is the twenty-minute pass that closes the gap: build, load unpacked, sign in at app.patina.cloud first so the panel adopts the portal session, then ten URLs across Leah's set and Marcus's repeats, one row each. Four things are worth watching for specifically. Does the destination dropdown really reset to "Library only" between Marcus's two Herman Miller captures — that single answer decides whether thirty saves a day is survivable. Does the Pinterest pin break the live panel or merely degrade — the audit's throw came from jsdom's selector engine on a selector Chrome cannot throw on, so the expectation is that it degrades; confirm which. Is the confidence badge honest on RH's member price and on the Instagram post, or does it sell certainty it hasn't got. And which tear-sheet fields are simply absent — SKU, dimensions, materials, lead time, trade price, vendor — when you look at the panel as a working designer rather than as a diff. Note the surprises; those are the rulings nobody wrote down yet.

How this was measured

The extraction numbers come from jsdom, not a browser. jsdom has no layout engine, so getBoundingClientRect() returns zeros and the position-based half of image scoring never contributes — image counts and JSON-LD-derived values are representative, but the highest-scored image may differ from what the live extension picks. jsdom also has no innerText; the harness aliases it to textContent so the price fallback can run, which means hidden or off-screen price text a real browser would exclude can be picked up here. And one throw in the corpus — Pinterest — is jsdom's selector engine, not a defect Chrome would reproduce. Treat every figure above as a strong signal and Kody's walk as the confirmation.

Fixtures were harvested live on 29 August 2026 — full-header curl for eleven pages, a Chrome render-and-download for the four behind a WAF or client-rendered. Only those four had scripts and stylesheets stripped (JSON-LD kept), so getComputedStyle() background-image lookups see nothing on them; the eleven curl fixtures are raw. Six page screenshots were captured, not fifteen.
