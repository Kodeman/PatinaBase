# Architecture blueprint v1 (Plan agent, 2026-09-06) — verified against code; superseded by architecture/02-system-design.md

## Architecture blueprint (starting point for T2 — verified by a Plan agent against code; T2 re-verifies, T3 attacks)

**A. URL + route — `/pay/[token]`.** `/invoices/*` is in the AASA (`apps/client-portal/src/app/.well-known/apple-app-site-association/route.ts:35`) and the singular `/invoice/<x>` is also accepted by the app's routers (`apps/mobile/Patina/Patina/App/DeepLinking/DeepLinkHandler.swift:301`), so both are out. Files: `apps/client-portal/src/app/pay/[token]/page.tsx` (server, `force-dynamic`, `robots noindex`, `referrer no-referrer` — copy `plans/[token]/page.tsx:8-15`), `invoice-link.ts` (`server-only`, `createServiceClient()` → `rpc('resolve_invoice_link')`, strict payload parser), `invoice-sheet.tsx` (client; the restored old layout + the chooser moved from `components/threshold/payment-method-chooser.tsx`), `state/route.ts` (GET, no-store, re-resolves with `p_record_view=false` for the post-checkout poll). Middleware: add `isPayPage` to the public list (`middleware.ts:150-159`) and widen the no-store/noindex header block (`:140-144`). Checkout return: reuse `lib/threshold/checkout-return.ts`; one edit — `consumeCheckoutReturn` hardcodes `#letterbox`/`#road` (`:78`), add an optional `hash` param.

**B. Data — new table `public.invoice_links`** (not columns on `invoices`; `invoices` UPDATE paths are hash-pinned and a side table keeps a revoke history): `id, invoice_id → invoices cascade, token (64-hex, unique), token_hash (unique), status active|revoked, created_by, created_at, revoked_at, view_count, last_viewed_at`; partial unique `(invoice_id) WHERE status='active'`. RLS on, no policies, table grants revoked from PUBLIC/anon/authenticated (service_role only). **Store the raw token** (unlike `document_shares`): four server producers re-emit it for the invoice's life (invoice-send, webhook receipts, reminders, folio Copy link) and hash-only would force remint on every send, breaking "stays as a receipt". Mint: `AFTER UPDATE OF status` trigger `WHEN NEW.status='sent'` (shape `00291:343-347`) so every issue entry point is covered without touching `issue_invoice`/`issue_invoice_for_actor`; plus `ensure_invoice_link(p_invoice_id)` (service_role) as belt-and-braces; migration backfills every `sent|partially_paid|paid` invoice. `regenerate_invoice_link(p_invoice_id)` (authenticated, gated by `can_manage_invoice` 00397:1265) revokes + mints. `get_invoice_link(p_invoice_id)` (authenticated; client/designer/active studio member — the exact gate of `get_invoice_payment_options` 00428:743-750) returns `{token,status}` for the letterbox, folio and iOS. Grants idiom `00437:516-529`; regenerate `supabase/seed/00-legacy-grants.sql`.

**C. Read path — `resolve_invoice_link(p_token, p_record_view default true) RETURNS jsonb`**, SECURITY DEFINER, granted authenticated + service_role, **not anon** (`00429:1908-1911`; called server-side only). NULL for malformed/unknown/revoked/draft/**void**; `paid` resolves (receipt). Payload = `invoice{number,title,status,dates,currency,subtotal/tax/total/paid/balance,memo,project_name,is_studio_invoice}` + `line_items[]` + `payments[]{amount,surcharge,method,status,rail,received_at}` + `studio{name,logo_url,website}` via `resolve_studio_identity(project_id, designer_id, studio_id)` (00571:1318 — fixes the two-studio letterhead trap) + `designer_display_name`, `client_display_name` + `payment_options{card_surcharge_bps, check_remit_to}` + `pay{payable, has_payer}`. **Never**: any uuid, `internal_notes`, emails, `client_id/designer_id/project_id/studio_id`, stripe ids, `void_reason`, reminder/AR columns, payment `reference/recorded_by/note`. Enforced twice (SQL test + TS parser that rejects forbidden keys at any depth).

**D. Guest pay — new edge function `invoice-link-checkout`, `verify_jwt=false`** (precedents `fulfillment-evidence`, `site-request-guest`, config.toml:538-557). Do NOT flip `create-checkout-session` public — it serves po_payment + direct_order for signed-in callers and iOS. Body `{token, method: card|us_bank_account|check}`. Flow: shape-gate → `resolve_invoice_link_for_checkout(p_token)` (service_role definer; returns ids only when link active, invoice sent/partially_paid, balance>0) → NULL = `404 invoice_not_found`. Card/ACH → the same driver as today (lift `ensureStripeCustomer`, `startInvoiceCheckout`, surcharge line, `invoice-checkout-core.ts` into `_shared/`) with return URLs `/pay/<token>?checkout=success&session_id={CHECKOUT_SESSION_ID}` / `?checkout=cancelled`. **Payer = `coalesce(invoice.client_id, project.client_id)`** — the household profile — because `payer_id` is NOT NULL (00397:34), the claim RPC insists on it and its `stripe_customer_id` (00428:229-240), and `assertInvoiceSessionIdentity` checks `metadata.payer_id`; nothing in the ledger changes. `has_payer=false` (project invoice with no household) → page offers Mail a check only, function returns `409 invoice_link_no_payer`. Stripe customer creation falls back to `designer_clients.client_email` when the profile has no email. Signed-in `create-checkout-session` invoice returns also move to `/pay/<token>` (K1). Webhook settlement untouched; only its two letters (`stripe-webhook:418,517`) plus `invoice-send:259` and `invoice-reminders:353` switch to `invoiceLinkUrl()` from a new `_shared/invoice-links.ts`. In-app `deep_link: /invoices/<id>` rows stay (they route the iOS inbox by id).

**E. Mail a check (guest)** — same function, `method:'check'`; body of `invoice-check-intent/index.ts:170-290` lifted to `_shared/invoice-check-intent-core.ts`; the JWT function becomes a thin adapter.

**F. Signed-in surfaces.** Hooks `useInvoiceLink`, `useRegenerateInvoiceLink` in `packages/supabase/src/hooks/use-invoices.ts`; `packages/utils/src/invoice-link.ts` (pattern, `invoiceLinkPath`, `invoiceLinkUrl`). **Letterbox** (`components/threshold/letterbox.tsx`): keep `useNamedInvoice`, drop the checkout-return hooks, the `open` state, `Settlement`, and the print link; render number · balance · due · "Open the invoice" → `/pay/<token>`. Delete `settlement.tsx`; move the chooser + its test under `app/pay/[token]/`. **Print**: fold into the token page (`@media print`, "Print / save PDF") and retire `/invoices/[invoiceId]/print`; fix `retired-routes.ts:147-153` so `/invoices/<id>/print` folds instead of 404ing.

**G. iOS** — keep native `InvoiceDetailView`; its Pay swaps `create-checkout-session` for `get_invoice_link` and opens `/pay/<token>` in the existing `SafariView` (`InvoiceDetailView.swift:68-70`, `InvoicesAPIClient.swift:257-262`). AASA unchanged. Follow-up build; legacy JWT path stays valid meanwhile.

**H. Security posture.** 256-bit token, hash lookup, uniform NULL → one `DeadLink`; edge function collapses to 404. **Rate limit**: add a Cloudflare `ratelimit` binding (`PAY_LINK_RATELIMIT`, 60/min per `cf-connecting-ip`) to `apps/client-portal/wrangler.jsonc` (none exists today), checked in `invoice-link.ts` via `getCloudflareContext()` (pattern `lib/data/service-binding.ts:45-47`), skipped when the binding is absent. Headers: noindex, no-store, no-referrer. Stripe metadata unchanged; the token appears only in `success_url/cancel_url`. `?checkout=success` never trusted — the page polls `state` until the payload's own `status/amount_paid_cents` say so. Void → dead. A link holder can start a checkout attributed to the household payer — harmless (they pay with their own instrument; receipt goes to the client's email) but must be named in the deck.

**I. Tests + gates.** SQL `supabase/tests/billing/invoice_links_test.sql` (mint on issue, backfill, resolve happy/NULL cases, forbidden keys, regenerate gate, party gate, `has_function_privilege('anon', …)` false ×5) + register signatures in `supabase/tests/edge_api/public_rpc_authorization_contract_test.sql` and `platform_acl_compatibility_test.sql`. Client-portal Jest for page/parser/chooser/checkout-return hash/retired-routes/AASA-not-claimed; Playwright `tests/pay-link.spec.ts` modeled on `plans-link.spec.ts`. Gates: `pnpm supabase:reset` → `supabase test db`; `deno test --allow-all --config supabase/functions/deno.json supabase/functions`; `pnpm --filter @patina/supabase type-check test` + `db:generate`; `pnpm --filter @patina/utils type-check test`; `pnpm --filter @patina/client-portal type-check test` (+ `env -u CI … test:e2e -- --project=chromium`); `pnpm --filter @patina/designer-portal type-check lint test`; `pnpm --filter @patina/admin-portal build`.

**J. Migration + deploy order.** `00574_invoice_links.sql` (table, trigger, backfill, 5 RPCs, grants). Order: (1) `supabase db push` — additive, backfill makes every open invoice linkable; (2) `./infra/deploy-portal.sh client-portal` — `/pay/[token]` live before any return URL points at it (the `create-checkout-session/index.ts:288-300` rule); (3) `./infra/deploy-portal.sh designer-portal`; (4) `supabase functions deploy invoice-link-checkout create-checkout-session stripe-webhook invoice-send invoice-reminders invoice-check-intent` + `[functions.invoice-link-checkout] verify_jwt=false` in config.toml; (5) iOS follow-up. ## Fable's review notes — T2 must answer, T3 must attack

1. If the raw token is stored, `token_hash` is redundant (a DB reader sees both). Recommend one `token` column with a unique index, resolve by equality; keep the hash only if T2 finds a concrete benefit.
2. Void → generic dead link (K2) vs a "withdrawn by {studio}" state with no amounts: the token is unguessable, so the softer state leaks nothing. Deck lists this as an owed ruling; default stays dead-on-void.
3. Confirm `designer_clients.client_id NOT NULL → profiles` means every rostered household already has a profile row (so `has_payer=false` is truly rare), and what `profiles.email` holds for a never-signed-up household.
4. PostHog events for the guest page (the old page fired `invoiceView / paymentMethodSelected / paymentStarted / paymentCompleted / paymentCancelled / checkIntentSubmitted`) — anonymous distinct_id; no PII in properties.
5. Reminder emails after a Regenerate must carry the new link (they call `ensure_invoice_link` → active row) — confirm; and confirm the receipt email after payment resolves the still-active link (paid links stay active).
6. Stripe Checkout `customer` vs `customer_email` — with `customer` set the email cannot be overridden; state what the guest sees prefilled and whether a household with a placeholder email gets an awkward prefill.
