### L07-01 — Signing a proposal is impossible when the designer belongs to two studios · **blocker · proposed T0**

**Where.** `supabase/migrations/00511_public_sd_hardening.sql:2418-2440` (the projects
`BEFORE INSERT` guard's studio discovery) reached through
`public._activate_proposal_as_project_impl` (`INSERT INTO projects` with no `studio_id`) ←
`_sign_proposal_authorized_00400` ← `sign_proposal(uuid,text)` ←
`apps/mobile/Patina/Patina/Services/API/ProposalsAPIClient.swift:405-418`.
Surface: `Features/Proposals/Views/ProposalSignSheet.swift`, reached from
`Features/Proposals/Views/ProposalDetailView.swift`.

**Evidence — counterfactual, both directions, same call.**

With the seeded designer in **two** active `design_studio` orgs:

```
curl -s -X POST .../rest/v1/rpc/sign_proposal -d '{"p_proposal_id":"b0000000-…-0002","p_signed_name":"Client User"}'
{"code":"P0001","details":null,"hint":null,"message":"studio_id_not_designer_studio"} [HTTP 400]
```

Then, with the second studio suspended so the count is **one**, the identical call:

```
{"id": "b0000000-0000-0000-0000-000000000002", "status": "accepted",
 "signed_at": "2026-09-02T14:28:23.287934+00:00",
 "project_id": "70df4fbc-55a3-44ad-bb26-a8e3791e6e57",
 "accepted_at": "2026-09-02T14:28:23.287934+00:00", "newly_signed": true} [HTTP 200]
```

The count the trigger computes, measured directly, was `2` before and `1` after:

```sql
SELECT count(DISTINCT membership.organization_id)
FROM public.organization_members AS membership
JOIN public.organizations AS studio ON studio.id = membership.organization_id
WHERE membership.user_id = <designer>
  AND membership.status = 'active' AND membership.role <> 'guest'
  AND studio.type = 'design_studio' AND studio.status = 'active'
  AND public.has_designer_domain_role(<designer>);
```

The guard's own comment says it: *"Zero or multiple candidates remain NULL and fail closed below."*
`proposals` has no `studio_id` column, so the activation has nothing unambiguous to fall back on.

**On glass.** `shots/w0-l0.7/01e-after-sign.png` — the sheet prints
*"We couldn't record your signature. Nothing has been signed."* and `proposals.status` stays `sent`.
The copy is correct and the mapping is deliberate (`ProposalSignError.map`, `.unexpected` carries no
payload by SP-15 / C5 design), so the client is told the truth and given no route forward.

**Why it is a round-one blocker.** Round one is Leah's active design clients and the proposal is the
first thing they are asked to act on. Leah is a studio owner; if she is a member of any second active
studio, **every** proposal signature fails with a message that names nothing. This is not
root-specific — it is server-side and fails identically on both roots.

**Fix sketch (not this lane's to make).** Give the activation an unambiguous studio: either carry
`designer_clients` → studio onto the proposal and pass it to the `projects` INSERT, or have
`_activate_proposal_as_project_impl` resolve the studio from `proposal.designer_client_id` rather than
from "the designer's only studio". Effort **M**. Route: **L0.2** (it owns the SQL) with an
`L1-B`/`L1-E` follow-up only if the client-side copy changes.

**Kody-run probe before build 1** (read-only, one line, no placeholders) — in `l07-notes.md` §3.
