## C7-01 — ModelContainer failure is `fatalError`; no fallback, no MigrationPlan
area persistence / prod-readiness · severity **blocker** · testerVisible yes · confidence 0.9
where `Patina/Core/Persistence/PersistenceController.swift:25-48`

```swift
do {
    container = try ModelContainer(for: schema, configurations: [configuration])
} catch {
    fatalError("Failed to create ModelContainer: \(error)")
}
```
The container is built from a bare `Schema([...])` with **no `VersionedSchema` and no
`SchemaMigrationPlan`** — lightweight migration only. Any change SwiftData cannot infer
(a new non-optional stored property without a default, a renamed/retyped property, a
changed `@Attribute(.unique)`) makes `ModelContainer(for:)` throw, and the app then
traps *inside `PatinaApp.init()`* — before the first frame, with no alert, no recovery,
no "reinstall" hint.
Why it matters: round-1 testers install build 1 and then get build 2. If build 2 touches
the schema, every tester's app crash-loops on launch and the only fix is delete-and-
reinstall (losing their rooms/scans). This is the single highest-cost latent defect in
the lane.
Fix: add a `SchemaMigrationPlan`; on `catch`, fall back to a fresh store (move the old
file aside) or an in-memory container plus a designed "we had to start your data over"
screen — never `fatalError` in a shipping build.
effort M

## C7-02 — `BoardModel` is used against a container whose Schema does not contain it
area browse-saved / persistence · severity **blocker** · testerVisible yes · confidence 0.7
where `Patina/Core/Persistence/PersistenceController.swift:26-35` (schema list) vs
`Patina/Core/Models/BoardModel.swift:12-13` (`@Model public final class BoardModel`),
`Patina/Features/Collections/ViewModels/CollectionsViewModel.swift:49` (`FetchDescriptor<BoardModel>`),
`:146-148` (`context.insert(board)`), `:202`, `Features/Collections/Views/CollectionsView.swift:137`
(`Button("Create") { viewModel.createBoard(context: modelContext) }`)

The shared container's schema is exactly:
`TableItemModel, RoomModel, SavedItem, StylePreferenceModel, SyncQueueItem, RoomScanPackage,
DesignRequestDraft, SubmittedDesignRequest`. `BoardModel` is **not** in it, is not reachable
by relationship from anything in it, and `PatinaApp.swift:98` installs that one container as
the only `.modelContainer`. `LocalStoreReset.wipeUserScopedData()` (`:27-34`) likewise deletes
those eight and not `BoardModel` — the same omission, twice.
`CollectionsView` is live on both roots (`ContentView.swift:273,310`;
`Features/Navigation/HouseFirstRoot.swift:214,240`), reached by the `.table` / `.roomSavedItems`
routes. `loadData` fetches boards on appear; the "New Board" alert inserts one.
Failure scenario: fetching/inserting a model absent from the container's schema raises a
Core Data `NSInvalidArgumentException` ("could not locate an NSEntityDescription for entity
name") — an ObjC exception, which `try?` on line 49 cannot catch. Best case the fetch is a
silent empty and Create is a no-op; worst case Saved crashes on open.
Not verifiable statically which of the two it is — needs a sim run of Pieces → Saved →
New Board on the steward's signed build.
Fix: add `BoardModel.self` to the schema (and to `LocalStoreReset`), or delete the boards
feature from `CollectionsView` if it is not meant to ship.
effort S

## C7-03 — Release-only `fatalError` behind an `@Entry` environment default
area first-run / prod-readiness · severity **major** · testerVisible yes · confidence 0.45
where `Patina/App/Coordinators/AppCoordinator.swift:761-767` and `:770-772`

```swift
static var environmentDefault: AppCoordinator {
    #if DEBUG
    return AppCoordinator()
    #else
    fatalError("AppCoordinator was read from the environment without being injected")
    #endif
}
...
@Entry public var appCoordinator: AppCoordinator = .environmentDefault
```
46 views read `@Environment(\.appCoordinator)`. In DEBUG the default silently manufactures a
coordinator; in a TestFlight (Release) build the same read is a hard trap. No detached
`UIHostingController` reads it today (the five `UIViewControllerRepresentable`s are Safari,
QuickLook, EventKit, and a pop-gesture shim), so it is dormant — but the asymmetry means
**every walk in this audit runs the branch that cannot crash**, and the branch that can is
only ever exercised by testers.
Fix: return a no-op/inert coordinator in Release too, or make the environment value optional
and let readers degrade.
effort S

## C7-04 — `session(_:didUpdate frame:)` retains the ARFrame and runs the whole capture pipeline on the main actor at 60 Hz
area rooms-scan / performance · severity **major** · testerVisible yes · confidence 0.85
where `Patina/Features/Walk/Services/RoomCaptureService.swift:868-901`

```swift
nonisolated public func session(_ session: ARSession, didUpdate frame: ARFrame) {
    Task { @MainActor in
        ...
        await self.frameCaptureService.captureFrame(from: frame)
        self.posedPhotoService?.consume(frame: frame)
        ... recorder.consume(frame: frame, ...)
        self.frameSinks.broadcast { $0.capture(frame: frame, timestampSeconds: instrumentTimestamp) }
    }
}
```
Two defects in one shape. (a) The `ARFrame` is captured by an escaping `Task`, so it is
retained past the delegate's return — ARKit documents that holding `ARFrame`s exhausts the
camera image buffer pool and stalls the session. (b) One `Task` is created per AR frame
(~60/s) and every downstream sink then runs *on the main actor*: hero-frame capture, posed
photos, depth recording, and `frameSinks.broadcast`. The scan UI is competing with its own
pipeline for the main thread.
Fix: do the pose/timestamp extraction synchronously inside the delegate, hand plain
`Sendable` values (pixel buffer copy or an already-encoded payload) to a dedicated actor,
and never let the `ARFrame` escape the callback.
effort L

## C7-05 — A new `CIContext()` per captured hero frame, on the main actor, mid-scan
area rooms-scan / performance · severity **major** · testerVisible yes · confidence 0.85
where `Patina/Features/Walk/Services/FrameCaptureService.swift:17` (`@MainActor`), `:247`

`let context = CIContext()` is constructed inside the per-frame compression path (interval
2.0 s, `:41`), then used to render + HEIC/JPEG-encode the frame (`:247-258`). `CIContext`
construction compiles kernels and allocates GPU state; doing it every two seconds on the main
actor during an AR session is a visible hitch generator. `PosedPhotoService` gets this right
— it builds one shared context at init (`PosedPhotoService.swift:72-73`).
Fix: hoist to a single lazily-created `CIContext`, and move the encode off the main actor.
effort S

## C7-06 — Launch housekeeping does recursive disk enumeration and directory deletes on the main actor
area performance-resilience · severity **major** · testerVisible yes · confidence 0.8
where `Patina/PatinaApp.swift:120-123`; `Core/Persistence/ScanDiskBudget.swift:19` (`@MainActor`),
`:110-155`, `:159-183`; `Core/Persistence/ScanRecoveryService.swift:41` (`@MainActor`),
`:412-441`, `:436-443`

`.task(priority: .utility)` sets the *task* priority, but every callee is `@MainActor`, so all
of this hops straight back to the main thread on the first frame:
* `ScanHoldMigrator.migrateIfNeeded` — fetch + save.
* `ScanDiskBudget.evictIfNeeded` — fetches every `RoomScanPackage`, then
  `FileManager.removeItem(at:)` on whole bundle directories (budget is 3 GB / 20 bundles),
  then `context.save()`. Deleting a multi-hundred-MB directory synchronously on the main
  thread is a watchdog risk on a cold launch.
* `ScanRecoveryService.scanForRecoverableSessions` → `bundleByteCount(at:)`
  (`FileManager.enumerator` over every file in every non-resting bundle, reading
  `.fileSizeKey` per entry) and `countPhotos` (`contentsOfDirectory`).
Fix: make these `nonisolated`/actor-isolated file passes, hand back plain values, and touch
the `ModelContext` on the main actor only for the mutations.
effort M

## C7-08 — Every PostgREST client silently downgrades to anon when the token is unavailable; RLS then answers `[]` and the screen says "you have nothing"
area money / messaging / rooms / prod-readiness · severity **major** · testerVisible yes · confidence 0.8
where the shared `applyHeaders` shape, e.g.
`Core/Network/RoomsAPIClient.swift:211-220`, `Core/Network/NotificationsAPIClient.swift:43-54`,
`Core/Network/DecisionsAPIClient.swift:235-246`, `Core/Network/ProductAPIClient.swift:26-34`,
plus `MessagingAPIClient`, `ProjectsAPIClient`, `FulfillmentAPIClient`, `RosterAPIClient`,
`EditorialStoriesAPIClient`, `InvoicesAPIClient`, `ProposalsAPIClient`, `DocumentsAPIClient`

```swift
request.setValue(APIConfiguration.anonKey, forHTTPHeaderField: "apikey")
if let token = await authToken() { request.setValue("Bearer \(token)", ...) }
```
`authToken()` is `try? await ...auth.session.accessToken` — a failed refresh, an expired
refresh token, or a keychain read failure returns `nil` and the request goes out as `anon`.
Owner-scoped RLS then matches nothing and PostgREST returns **HTTP 200 with `[]`**. Nothing
downstream distinguishes that from "this account genuinely has no decisions / invoices /
messages / rooms".
Failure scenario: a tester leaves the app for a month, opens it on a plane, and Studio,
Messages, Invoices and Spaces all render their designed empty states as if the account were
new. `RoomScanSyncService` has the same hole via `resolveUserId()`
(`RoomsAPIClient.swift:402-405` → `currentUserId()` `:204-209`).
Fix: make the token non-optional for owner-scoped reads — throw `.notAuthenticated` when it
is missing and let the UI say "we couldn't reach your account", never "empty".
effort M

## C7-12 — Everything expensive at launch is synchronous, in `PatinaApp.init()`, before the first frame
area performance-resilience · severity **major** · testerVisible yes · confidence 0.8
where `Patina/PatinaApp.swift:63-89`

In order, all synchronous, all before `body` is evaluated:
1. `PatinaFonts.registerAll()` (`:64`) → `CTFontManagerRegisterFontURLs` over **18 TTFs,
   2.97 MB** (`PatinaDesignKit/.../PatinaFonts.swift:23-25`), plus a `Bundle.module` resource
   enumeration.
2. `PostHogService.shared.initialize()` (`:76`) → `PostHogSDK.shared.setup(config)`

floor for "first interactive frame" is ~2 s *after* all of the above.

## C7-13 — Telemetry queue re-queues failed batches without bound and rewrites the whole file every 30 s
area performance-resilience · severity **major** · testerVisible yes · confidence 0.75
where `Patina/Services/Analytics/DailyRoomBatchQueue.swift:70-78`, `:81-90`, `:94-101`

```swift
let ok = await DailyRoomAPI.shared.postBatch(...)
if !ok { pending.insert(contentsOf: batch, at: 0); await persistToDisk() }
```
`maxBatchSize` (100) only *triggers* a flush; it never caps `pending`. The endpoint is
`client.patina.cloud/api/interactions/batch` (`DailyRoomAPI.swift:34`) — a client-portal
route whose deploy is still on the OWED list from the Daily Return program. If it 404s (or

`Application Support/daily_room_queue.json`. Battery, disk, and an ever-slower flush.
Fix: cap `pending` (drop oldest), add backoff on repeated failure, and stop persisting on
every failed tick.

## C7-15 — A forced token refresh before *every* artifact upload
area rooms-scan / auth · severity **major** · testerVisible yes · confidence 0.6
where `Patina/Services/Sync/BackgroundScanUploader.swift:146-156`

```swift
try? await SupabaseClientManager.shared.client.auth.refreshSession()
```
runs per artifact, and a bundle has many artifacts (manifest, USDZ, world map, meshes, depth,
photos). GoTrue rotates refresh tokens and rate-limits `/token`; a burst of forced refreshes

## What is GOOD (calibration)

* **Flag resolution is honest and once-only.** `FeatureFlags` (`Core/State/FeatureFlags.swift`)
  reads PostHog's persisted payload synchronously, states the "off on first launch" cost in
  the file header instead of hiding it, and `AppCoordinator.isHouseFirstRoot` is a `let` so a
  late payload can never swap the root under a running session.
* **Session-change hygiene is genuinely well built.** `AuthService.applySession` funnels all
  nine session-install sites through one seam; `SessionScope` enumerates every singleton that
  holds account data and has a test that fails on any unlisted `static let shared`;
  `LocalStoreReset` remembers the non-SwiftData homes (App Group snapshot, `LastSeenStore`,
  `StyleProfileStore`).
* **Coalescing where it matters.** `RecordForeground.coalesce`, `BadgeCountService.inFlightRefresh`,
  `RoomSyncCoordinator.inFlight` (claimed before the first `await`, with the review note
  explaining why), and `DailyRoomViewModel`'s per-concern `Task` handles that cancel on re-entry.
* **Decode leniency on the money rail.** `RemoteInvoice`, `RemoteProposal`, `RemoteClientDecision`,
  `RemoteFulfillmentOrder` are all-optional; enum-ish columns are typed `String` and normalised in
  Swift. `Product.init(from:)` is the U39 fix done properly.
* **`DecisionsAPIClient.decisions(matching:)`** degrades a refused PostgREST embed (400) to a
  narrower select rather than losing the rows — the right instinct, and rare.
* **`ScanRecoveryService`'s `Disposition` enum** makes "the manifest won't decode" and "there is
  no bundle" impossible to conflate, and only deletes bytes it has proven are worthless.
* **U40 is fixed on main**: `QuietConversationFlowHost.acceptFallbackFloorPlan` /
  `persistFallbackRoom` (`:372-424`) persist the manually-entered room, idempotently, and land
  the user in it. Do not re-report it.
* **`PatinaAsyncImage`** exists at all, with designed loading/failure states and a retry tap —
  the SP-02 `Color.clear` overlay fix is a real one.

## What I could NOT verify, and why

* **Whether C7-02 crashes or silently no-ops.** Needs a run of Pieces → Saved → "New Board" on
  the steward's signed Debug build. Static reading cannot tell an ObjC exception from a swallowed
  Swift throw here.
* **Every ARKit/LiDAR claim (C7-04, C7-05, C7-35) and the non-LiDAR fallback (C7-10).** The
  Simulator has no ARKit camera pump and `RoomCaptureSession.isSupported` is false there, so the
  cost and the fallback chain are source-read only. C7-10 needs a non-Pro device or a
  `RoomCaptureService.isSupported`-forced build.
* **Actual cold-launch timings (C7-12).** No Instruments trace; the 18 fonts / 2.97 MB and the
  1.5 s + 0.5 s splash floor are file facts, the resulting milliseconds are not measured.
* **Whether `client.patina.cloud/api/interactions/batch` answers in production** (C7-13's
  severity hinges on it). The route exists in the repo; the client-portal deploy is on the
  program's OWED list. Not probed — this lane is read-only and must not touch production.
* **C7-03 firing in Release.** No detached hosting controller reads the coordinator today; the
  risk is the DEBUG/Release asymmetry, not a located crash.
* **The test target's warning count.** The captured `xcodebuild.log` is an app-only build
  (0 warnings attributed to `PatinaTests`/`PatinaUITests`), so C7-16's numbers cover the app
  target only.
* **`aps-environment: development` in the checked-in entitlements.** Xcode's automatic signing
  usually rewrites this from the distribution profile at archive time; I could not confirm what
  the actual TestFlight archive carries, so I have not raised it as a finding. Worth one probe
  by whoever owns testflight-config.
