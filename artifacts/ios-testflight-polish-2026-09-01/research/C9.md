# C9 — Device matrix and screen sizes (static audit)

Lane: C9. Read-only. Repo tip at kickoff d7287c3f8. App: apps/mobile/Patina.
Scope: layout code under Features/**/Views + Design/**; fixed widths/heights,
GeometryReader, UIScreen.main, magic device widths, sheets, keyboard, iPad,
deployment target, portrait lock, status bar / home indicator collisions.

Claim levels: everything below is **compile/source-verified** (read on main) unless
marked otherwise. One item is **sim-verified** from an existing steward screenshot
(`shots/steward/c-session.png`, iPhone 17 Pro 402x874). Nothing here is device-verified.

## C9-01 — The build ships to iPad (device family "1,2") with zero iPad layout code
- area: testflight-config · severity: major · testerVisible: true · confidence: 0.95 · effort: S
- where: `apps/mobile/Patina/Patina.xcodeproj/project.pbxproj:511,543,712,760,781,803,823,843` (`TARGETED_DEVICE_FAMILY = "1,2"`)
- evidence: every target sets `TARGETED_DEVICE_FAMILY = "1,2"`. A repo-wide grep over
  589 Swift files for `horizontalSizeClass`, `verticalSizeClass`,
  `UIUserInterfaceIdiom`, `UIDevice.current.userInterfaceIdiom` returns **zero
  matches** (only the English word "idiom" in comments). The root is a plain
  `NavigationStack` (`ContentView.swift:159-176`), never `NavigationSplitView`.
  Every `LazyVGrid` in the app uses a fixed count of `GridItem(.flexible())` —
  `RecommendationsView.swift:268-271` (2), `ScanFallbackEntryView.swift:99` (3),
  `ProjectDetailView.swift:91-98` (2), `HeroPickerSheet.swift:29` (2),
  `VisualResonanceView.swift:37` (2), `MaterialConnectionView.swift:43` (2),
  `StyleQuizView.swift:229` (2) — not one `GridItem(.adaptive(minimum:))`.
- why it matters: TestFlight will offer this build to any iPad the tester owns, and it
  installs as a native iPad app (not compatibility mode). Every screen becomes a
  1000pt-wide stretched phone: 2-column product grids with ~470pt cells,
  full-bleed body text with no measure limit, a 280pt-max house rail card floating
  in a 1000pt row. A homeowner opening it on an iPad judges the app unfinished in
  two seconds.
- fix: for the first TestFlight set `TARGETED_DEVICE_FAMILY = 1` (iPhone only) on the
  app + widget targets. A real iPad pass (size classes, adaptive grids, a text
  measure cap) is a later program, not a polish item.

## C9-02 — IPHONEOS_DEPLOYMENT_TARGET 26.5, but nothing in the app needs above 26.0
- area: testflight-config · severity: major · testerVisible: true · confidence: 0.9 · effort: S
- where: `project.pbxproj:494,526,600,658,693,741,772,794` (`IPHONEOS_DEPLOYMENT_TARGET = 26.5`)
- evidence: the **highest** availability floor anywhere in the app or widget is
  `iOS 26.0`. Full list of `#available` guards: `ARPlacementView.swift:237,248`
  (`glassEffect`, "iOS 26.0"), `CompanionOverlay.swift:1141` ("iOS 26.0"),
  `ProductDetailBlocks.swift:213` ("iOS 26.0"), plus three legacy 14.x/18.0 guards
  (`ScanBundleWriter.swift:101`, `PostHogService.swift:70`,
  `ARPlacementManager.swift:66`). Grep for any 26.1+ surface
  (`tabBarMinimizeBehavior`, `scrollEdgeEffect`, `backgroundExtensionEffect`,
  `tabViewBottomAccessory`, `FoundationModels`, `AlarmKit`, `SpeechAnalyzer`,
  `WebView`) returns nothing. The widget's newest API is `containerBackground`
  (iOS 17, `HouseWidgetViews.swift:39-48`). PatinaDesignKit's own floor is
  `.iOS("17.6")` (`PatinaDesignKit/Package.swift:26`). SPM pins are
  supabase-swift 2.40.0 and posthog-ios 3.48.0 — both far below 26.
- why it matters: TestFlight refuses the install outright on any invited tester still
  on 26.0–26.4 ("requires iOS 26.5"). Kody's first round is small; losing even one
  invitee to a version floor nothing in the code needs is pure self-harm. It also
  makes every `if #available(iOS 26.0, *)` in the app a compiler-warning dead branch.
- fix: set `IPHONEOS_DEPLOYMENT_TARGET = 26.0` on all targets, build, and confirm no
  new availability errors. The three `glassEffect` guards then become load-bearing
  again rather than always-true.

## C9-03 — Today's scroll ends in 240 pt of dead canvas (double bottom reservation)
- area: today-home · severity: major · testerVisible: true · confidence: 0.85 · effort: S
- where: `Features/Home/Views/DailyRoomView.swift:371` (`Spacer().frame(height: 120)`)
  + `ContentView.swift:185` (`.companionHearthReservation(isActive:)`)
- evidence: `ContentView` applies `.companionHearthReservation` to the whole
  `NavigationStack`, which adds a `safeAreaInset(edge: .bottom)` of
  `CompanionHearthMetrics.reservation(...)` = **120** at normal text size
  (`Design/Components/CompanionSafeArea.swift:178-186`, `:148-151`). `DailyRoomView`
  — the flag-off root's home, which every first-round tester lands on — *also*
  appends its own `Spacer().frame(height: 120)` at the end of its column. The two
  stack: 240 pt of empty canvas above the home indicator, for a dock that is
  documented at **140** (`CompanionSafeArea.swift:33-40`: "mark 64 + gap 4 +
  caption row 44 + lift 28 = 140"). ~100 pt of nothing.
- why it matters: the last thing the tester sees when they scroll Today to the end is
  a quarter-screen of blank. It reads as a page that failed to load, not as breathing room.
- fix: delete the local `Spacer().frame(height: 120)`; the root reservation already owns
  this edge. (Same class as C9-04 — one owner, one constant.)

  become 51–71 pt of dead space above a 49 pt bar.
- fix: replace all twenty with `CompanionHearthMetrics.pinnedFooterClearance(houseFirst:)`

## C9-05 — The message composer is drawn under the Companion dock (threadDetail never yields)

## C9-06 — The scan/AR headline features are gated to LiDAR-only iPhones (Pro models)
- area: rooms-scan · severity: major · testerVisible: true · confidence: 0.9 · effort: M
- where: `Features/RoomScan/Views/QuietConversationFlowHost.swift:151-158`;
  `Features/Walk/Services/RoomCaptureService.swift:241-242`;
  `Features/ARPlacement/ViewModels/ARPlacementViewModel.swift:115-117`
- evidence: `QuietConversationFlowHost.bootstrap()` does
  `let hasLidar = RoomCaptureService.isSupported` → `RoomCaptureSession.isSupported`,
  and routes to `step = .fallback` (`ScanFallbackEntryView`, a typed-dimensions form)
  when false. `RoomCaptureSession.isSupported` is true **only on LiDAR hardware**.
  Separately, `ARPlacementViewModel.supportsAR` is
  `ARWorldTrackingConfiguration.supportsSceneReconstruction(.mesh)` — also a
  LiDAR-only check, and *stricter than AR placement actually needs*: placing a USDZ
  on a detected plane works on every A12+ iPhone with plain world tracking;
  `ARPlacementManager.swift:40-44` already treats `.mesh` as optional
  (`if supportsSceneReconstruction(.mesh) { config.sceneReconstruction = .mesh }`).
- why it matters: of the plausible first-round tester devices, **iPhone 17 (base),
  iPhone Air and iPhone 16e have no LiDAR**. Those testers never see the room scan
  (the app's signature act) and are told "AR not supported" for a feature their
  phone can do. The invite says "scan your room"; the app says no.
- fix: (a) relax `supportsAR` to `ARWorldTrackingConfiguration.isSupported` and keep
  `.mesh` as the optional upgrade the manager already treats it as; (b) make the
  non-LiDAR path an intentional, first-class flow rather than a "fallback" — this is
  the majority of the tester pool, not the edge.

## C9-07 — INFOPLIST_KEY_UIStatusBarHidden = YES is inert; one screen hides the bar anyway
- area: visual-system · severity: minor · testerVisible: true · confidence: 0.9 · effort: S
- where: `project.pbxproj:691,739` (`INFOPLIST_KEY_UIStatusBarHidden = YES`);
  `Features/Home/Views/DailyStoryDetailView.swift:51` (`.statusBar(hidden: true)`)
- evidence: **sim-verified** — `artifacts/ios-testflight-polish-2026-09-01/shots/steward/c-session.png`
  (iPhone 17 Pro, 402x874) shows the status bar fully drawn: "9:41", cellular bars,
  Wi-Fi and battery. The plist key is dead because
  `UIViewControllerBasedStatusBarAppearance` is not set to `false` anywhere
  (grep over pbxproj + `Patina/Info.plist` finds no such key), so the hosting
  controller's `prefersStatusBarHidden` (false) wins after launch. The app's own
  chrome agrees the clock is there: `Design/Components/PatinaScreenChrome.swift:24-27`
  — *"Reserves the status-bar region on a scroll container so scrolled content
  passes BEHIND the clock"*. Meanwhile exactly one screen,
  `DailyStoryDetailView`, applies `.statusBar(hidden: true)`.
- why it matters: a build setting that says the opposite of what ships is a trap for
  the next person, and the one screen that *does* hide the clock makes it pop in and
  out as the tester opens and closes a story. On a Dynamic Island device hiding the
  status bar does not remove the island, so the story hero loses the clock and keeps
  the black pill.
- fix: drop `INFOPLIST_KEY_UIStatusBarHidden` (the app clearly wants the status bar),
  and decide whether the story detail's hide is intentional — if it is, it needs the
  same treatment on every full-bleed hero, not one screen.

## C9-08 — No keyboard-dismiss affordance exists anywhere in the app
- area: forms/auth · severity: major · testerVisible: true · confidence: 0.85 · effort: M
- where: repo-wide. Number/decimal pads with no return key:
  `AuthenticationView.swift:327` (`.numberPad`, the 6-digit sign-in code),
  `RoomBudgetSheet.swift:61` (`.numberPad`),
  `ManualRoomEntryView.swift:65` (`.numberPad`), `:133` (`.decimalPad`),
  `RoomSettingsView.swift:193` (`.decimalPad`),
  `ScanFallbackEntryView.swift:173` (`.decimalPad`).
- evidence: grep over all 589 Swift files finds **zero** `ToolbarItemGroup(placement: .keyboard)`,
  **zero** `.scrollDismissesKeyboard`, **zero** `endEditing`/`resignFirstResponder`/
  tap-to-dismiss, exactly **one** `@FocusState` in the whole app
  (`Collections/Views/SavedNoteSheet.swift:20,43,81`) and exactly **one** `.onSubmit`
  (`RoomSettingsView.swift:121`). `.submitLabel` appears twice, both on search
  fields (`ThreadListView.swift:110`, `ProjectListView.swift:107`).
- why it matters: a numeric pad has no Return key. Once the tester taps the sign-in
  code field, the budget field, or a room dimension, the only exit is whatever
  SwiftUI's default scroll behaviour happens to give them — and on the non-scrolling
  sheets (C9-09) there is no exit at all. It also means the auth form never focuses
  the email field on appear and never chains email → password, which is the single
  most-noticed friction on a first launch.
- fix: one shared `.keyboardDoneToolbar()` modifier applied to every numeric field,
  `.scrollDismissesKeyboard(.interactively)` on form scroll views, and a `@FocusState`
  chain on the auth form (autofocus email; Return moves to password / submits).

## C9-09 — RoomBudgetSheet: a number pad inside a single fixed `.medium` detent with no scroll
- area: money · severity: major · testerVisible: true · confidence: 0.7 · effort: S
- where: `Features/Rooms/Views/RoomBudgetSheet.swift:38-107`, presented at

  TextField at `:60-61` and the Save button below it at `:76-85`, presented at a
