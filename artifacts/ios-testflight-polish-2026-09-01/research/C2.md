## Findings

### C2-01 — A cold-launch notification tap is handled twice
- area notifications · **major** · testerVisible true · confidence 0.65 · effort S
- where `Patina/App/AppDelegate.swift:44-46` and `:141-155`
- evidence `didFinishLaunchingWithOptions` calls
  `handleNotificationPayload(userInfo, source: "cold_launch")` for
  `launchOptions[.remoteNotification]`; the `UNUserNotificationCenterDelegate` is installed
  one line earlier (`:42`), so iOS then also calls
  `userNotificationCenter(_:didReceive:)` → `handleNotificationPayload(userInfo, source: "tap")`.
  There is no seen-set, no `notification_log_id` dedupe, no launch flag.
  Each call does `DeepLinkHandler.shared.navigate(to: resolved)` → `coordinator.openExternal`
  → `push` / `tabs.append`, and each fires `NotificationsAPIClient.markOpened`.
- why A tester taps "An invoice is ready" from the Lock Screen with the app terminated and
  lands on the invoice with **two** copies of it on the stack: Back goes to the invoice
  again. It is the first impression of the whole notification rail.
- fix Dedupe in `handleNotificationPayload` on `notification_log_id` (or a
  `hasHandledLaunchPayload` flag set in `didFinishLaunching` and consumed by the first
  `didReceive`). The cleanest is to drop the `launchOptions` branch entirely — the
  `UNUserNotificationCenter` delegate covers the tap case on every supported iOS.

### C2-02 — A universal link that lands before the coordinator exists is dropped, and reported as handled
- area widget-deeplinks · **major** · testerVisible true · confidence 0.6 · effort S
- where `Patina/App/DeepLinking/DeepLinkHandler.swift:64-71` (vs the correct pattern at `:278-292`)
- evidence
  ```swift
  if let route = Self.route(forUniversalLink: url) {
      if let coordinator, coordinator.phase == .launching {
          coordinator.pendingDeepLink = url
      } else {
          coordinator?.openExternal(route)   // ← coordinator nil ⇒ silent no-op
      }
      return true                            // ← still claims "handled"
  }
  ```
  `configure(coordinator:)` runs from `ContentView`'s `.onAppear`
  (`PatinaApp.swift:102-105`) while `.onOpenURL` (`:99-101`) is registered on the same view,
  so the ordering is not guaranteed. The **widget** branch in the same file handles exactly
  this case correctly, stashing into `pendingRoute` (`:286-290`); the APNs branch does too
  (`:46-52`). Only the universal-link branch does not.
- why The tester taps an emailed invoice link with the app terminated; the app launches to
  Today and nothing else happens. There is no error and no retry — the link looks broken.
- fix Use the same stash-or-open pair the widget branch uses: when `coordinator == nil`,
  set `pendingRoute = route`.

### C2-03 — The Settings "Notifications" toggle is inert on every side
- area notifications · **major** · testerVisible true · confidence 0.9 · effort M
- where `Patina/Features/Settings/Views/SettingsView.swift:110-119`;
  `Patina/Services/Settings/SettingsService.swift:30,83,102,124`;

  `.notDetermined`, the row's action is the primer; when `.denied`, it deep-links to
  `UIApplication.openSettingsURLString` with one sentence. Have `apns-send` honour

## What is GOOD (calibration)

- **Both root dispatchers and `RouteTabTable` are exhaustive with no top-level `default:`**,
  deliberately, so a new `AppRoute` breaks the build in all three places
  (`RouteTabTable.swift:5-7`). That is the right shape and it holds today.
- **The universal-link table matches the live AASA exactly**, including the plural/singular
  aliasing, and the reasoning is written down at the point of decision
  (`DeepLinkHandler.swift:224-228` ↔ the AASA route's own comment).
- **`route(forUniversalLink:)` and `route(forWidgetLink:in:)` are pure static functions**,
  compiled into `PatinaTests` alongside the widget's own `PatinaWidgetLinks`, so the round
  trip is pinned rather than asserted in prose (`HouseWidgetPayload.swift:241-243`).
- **The widget's payload has no field to leak a count from.** `WidgetSnapshot` is a separate
  type from `HouseRecord` specifically so no future edit can put `needsYou` on a Lock Screen
  (`WidgetSnapshot.swift:5-17`) — a structural ruling, not a review comment.
- **The widget is honest when stale**: `refreshedLine(now:)` returns nil while fresh and
  "Refreshed N hours ago" past six hours, and the Lock Screen makes the same disclosure the
  Home Screen does.
- **`PushTokenService.detectEnvironment`** derives `aps-environment` per token from the
  embedded provisioning profile with a documented three-rung ladder, rather than `#if DEBUG`.
- **In-app tap vs. external entry are genuinely different verbs** (`navigate` pushes on the
  tab you are on; `openExternal` reads `RouteTabTable`), and the reason is written at both
  sites. Back behaviour on the four-stack root is correct.
- **`InvoiceReminder`** is the most carefully-built thing in this lane: it prints the exact
  sentence it will send before you opt in, refuses to offer itself when the moment has
  passed, cancels itself when the invoice stops being payable, asks for `[.alert]` only, and
  carries `entity_type: "invoice"` so its tap routes to the invoice.
- **The guest state of the notification feed invites rather than errors**
  (`NotificationFeedView.swift:187-201`), and `NotificationsViewModel.merge` solves a real
  bell-vs-Studio contradiction with per-entity coverage rather than a blunt kind filter.
- The record/widget files are deleted at the auth boundary (`LocalStoreReset.swift:63-67`),
  which is why the widget payload needs no owner id.
