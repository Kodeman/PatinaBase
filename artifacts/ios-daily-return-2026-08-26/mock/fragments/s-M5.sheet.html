s-M5 · The system prompt · screen sheet
PurposeShow what the primer buys: one iOS prompt, once per install, arriving after a person already knows what they are being asked for.
Entry points“Turn on notifications” on s-M4 — the only path. iOS shows this alert once; there is no second chance in the same install.
ComponentsSystem: UNUserNotificationCenter.requestAuthorization’s alert, drawn to Apple’s metrics (270 pt, 14 pt radius, hairline-split buttons, #007AFF, the right-hand button semibold). Existing: PushTokenService.requestAuthorization and its one-per-install guard.
CopyApple’s, not ours: “‘Patina’ Would Like to Send You Notifications” / “Notifications may include alerts, sounds and icon badges. These can be configured in Settings.” / “Don’t Allow” · “Allow”. The only copy we control is the screen behind it.
DataOn Allow: the APNs token registers into device_push_tokens through the existing service. Nothing else is written.
StatesAllow → token stored, the pushes SP-08 describes can send. Don’t Allow → nothing is sent; the in-app feed and email carry the same events, which is why declining is cheap. The one-per-install guard is kept, so a silent prompt that never fires is a regression to watch for.
InteractionsTwo buttons, Apple’s. Analytics: the same push_permission_prompted event carries the outcome.
TierEngaged and activeProject only — the prompt is reached only through s-M4.
Callouts1 · Apple’s alert, Apple’s words — nothing here can be tuned, which is the whole argument for the screen behind it. 2 · the decline is not a dead end: the feed and email still carry every event. 3 · and it is final for this install — iOS will not ask twice, so the primer is the only lever we have.
New vs todayOnly the moment it fires. Today this same alert appears immediately after a design-request submission, with nothing in front of it.
