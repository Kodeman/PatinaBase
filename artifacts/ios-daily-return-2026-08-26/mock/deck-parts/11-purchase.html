The purchase path, both ways

Money moves through the same hosted Checkout in either direction. What differs is who is owed a name when it settles.

Both directions build on the rail that already ships — public.direct_orders, create_direct_order, and create-checkout-session’s existing direct-order branch — rather than a second one. Money is taken in hosted Stripe Checkout inside SFSafariViewController, the same container the invoice screen already opens, and Apple Pay is already inside it (C25). Neither direction proposes a native PaymentSheet: it buys one fewer context switch and costs an SPM dependency, a merchant-id entitlement and a re-do of ACH and settle-polling that already works. On compliance the two are a tie on substance — physical goods, external payment, no IAP (App Review 3.1.3(e) / 3.1.5(a)); Sign in with Apple already ships, so 4.8 is satisfied; neither direction sells a digital good in-app, so 3.1.1 stays shut — and Direction A alone spends a sentence arguing it, naming the design-fee invoice already on this same Checkout as a service under 3.1.3(d)/(e) rather than asserting there is no service in the app. Both correctly flag SP-20’s account deletion (5.1.1(v)) as release-gating regardless of which way this goes.

The state machine, shared by both

  • create_direct_order → pending_payment → canceled, or checkout.session.completed → paid → refunded (an existing trigger, 00277).
  • Settle enqueues fulfillment_intake, which mints the fulfillment row idempotently from the PaymentIntent.
  • fulfillment_orders status is derived from line state, never a text column: intake → transmitted → acknowledged → in production → shipped → delivered → settled.
  • A damage claim lands in fulfillment_exceptions, with an evidence window on the rail the order already joined.

Today that machine stops at paid and no client-readable order exists at all — the client rail is unbuilt in both documents, so every purchase claim here is a read against migrations and edge functions, not a walk.
