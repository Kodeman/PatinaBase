# Mood Board UX Audit — Panel Finding: Information Architecture / Workflow Lens

## Findings

**IA-1 | P1 | confidence high | Entry-point architecture | new** — Every path to create a NEW proposal now yields a Boards-less drafting room, stranding the feature's front door. Evidence: `apps/designer-portal/src/lib/document/commercial-documents.ts` `commercialDocumentExperience()` maps `design_services`/`service_addendum` → `'design_services'`; `drafting-room.tsx:195-196` routes that straight to `ServiceAgreementDraftingRoom`, which prints "N of **7** facets" (`service-agreement-drafting-room.tsx:269`) and has zero import of `BoardsBuilder` — the 8-facet `DraftingRoomEditor` that hosts Boards is unreachable. Matches prod-test F7 (every creation path in prod — ⌘K, Desk quick action, lead→discovery — creates `design_services`). No PRD/ruling anywhere addresses this; it postdates the MoodBoard GA (2026-08-03) and looks like an unannounced side-effect of the later commercial-document-kind split. → Decide deliberately whether Boards belongs in the service-agreement flow or whether the real new front door is now project-level only (then fix IA-2/IA-3 first, since that's where new work lands).

**IA-2 | P1 | confidence high | Ownership-split defect | new** — Blank-board creation on a PROJECT owner is coded to always throw, yet the UI calls exactly that path. `useUpsertBoard` (`packages/supabase/src/hooks/use-boards.ts:594-596`) explicitly throws `'Project board changes require apply_board_room_state'` when `mutationOwner(input).kind === 'project'`. `BoardsBuilder.handleBlank` (`boards-builder.tsx:179-189`) calls this hook unconditionally for both owner kinds — the literal source of prod-test F1. Contrast: `useMaterializeBoardTemplate` (`use-board-templates.ts:79-113`) routes through the owner-aware `materialize_board_template` RPC for both kinds, which is exactly why "Patina starters" work from the same dialog while "Blank board" doesn't. → Route project-owned blank creation through an owner-aware RPC (mirror the template path) rather than the guarded client-side insert.

**IA-3 | P1 | confidence high | Ownership-split feature gap | new** — Share exists end-to-end at the data layer for project-owned boards, but the UI deliberately never offers it. `board-room-shell.tsx:912-914` gates the Share button on `owner.kind === 'proposal'` — an explicit condition, not a missed wire-up. Yet `06-acceptance-evidence.md` AC2.16 is Passed: "SQL-SHARE now mints, resolves, and revokes a board with `project_id` set and `proposal_id` null." Backend readiness plus a one-line UI gate = a cheap, low-risk fix, unlike a net-new feature. → Drop the owner-kind condition on the Share button; the hard part (RPC/security) is already done and tested.

**IA-4 | P1 | confidence high | Entry-point regression | ruled (Ruling #1)** — The desk-level "recent boards" entry Ruling #1 promised ("boards become first-class at desk/document level") was built, mounted, and observed working in prod (AC1.3's PROD-PROBE saw `mood_board_opened` with `source=desk_recents`), then silently dropped three weeks later. `git log`: `RecentBoardsStrip` mounted into `desk/page.tsx` in `21127d615` (2026-08-03, GA day); commit `51986bbc0` "B2-L2 the Desk roster" (2026-08-26) rewrote `desk/page.tsx`, deleting the `RecentBoardsStrip` import/render while swapping in `DeskRoster` — no replacement recency surface was added. The component + its test file remain intact and orphaned (repo-wide grep: zero references). → Re-mount it (or fold its intent into `DeskRoster`); the fix is nearly free since the component is untouched and tested. Flagging as ruled because current code actively reverses a shipped piece of a locked decision — worth a deliberate re-ruling, not a silent drift.

**IA-5 | P2 | confidence medium | Workflow duplication | new** — Two independent "start a board" implementations exist for the same verb with silently different capability. `BoardsBuilder` (drafting facet, `project-mood-boards.tsx`, `project-boards-view.tsx`) opens a picker (blank/Patina starters/studio templates). `worktable/boards-strip.tsx`'s `startBoard()` (lines 108-136) reimplements creation independently — blank-only, no picker, same underlying `useUpsertBoard` call — and per its own doc comment is proposal-keyed only, so its boards disappear from that surface once the document activates to a project. → Either give the worktable strip the same picker or relabel the action so the narrower affordance is legible ("Quick board").

**IA-6 | P2 | confidence medium | Naming/findability | new** — Every creation surface defaults to `Board ${n+1}` with no naming prompt (`boards-builder.tsx:185`, `boards-strip.tsx:119`) — confirmed in practice by prod-test's own "clean 'Board 2'" artifact. Boards are addressed across owners in ⌘K/desk recents where the owner/room name is the only disambiguator; within one project with several blank boards, item count is the only other cue. → Prompt for a name (or seed a smarter default) at least in the modal pickers, which already stop the flow.

**IA-7 | P2 | confidence medium | Dead-end state | new** — No hard delete for boards; archive is a one-way door with no visible "view archived" affordance. Prod-test confirms no hard-delete UI exists anywhere. `BoardsBuilder` shows "N archived" (`boards-builder.tsx:228-232`) as plain text, not a link; `project-mood-boards.tsx`/`project-boards-view.tsx` simply filter `status !== 'archived'` and drop the rest — archived boards become permanently unreachable from any UI I read. By contrast board **templates** made from boards DO have a real Delete (prod-test follow-up). Boards have less lifecycle control than artifacts derived from them. → Surface an archived-boards list behind the count, even read-only.

**IA-8 | P2 | confidence medium (expert judgment) | Lifecycle legibility asymmetry | new** — Draft→freeze→continue is well-explained on project surfaces but invisible at authoring time. `project-mood-boards.tsx`/`project-boards-view.tsx` clearly split "Working boards" vs "Signed direction" (frozen) with an explicit idempotent "Continue in project" action — genuinely good design. But `BoardsBuilder` as mounted in the Drafting Room's Boards facet gives zero forward-looking signal that these boards will freeze at signing or what "continue" means later. → A one-line note in the facet closes this cheaply.

**IA-9 | P3 | confidence high | Schema/terminology trap (root cause class for IA-2) | new** — The table literally named `proposal_boards` doubles as the LIVE project-owned boards table (via a populated `project_id` column), while a separately-named `project_boards` table holds FROZEN snapshots. `useProjectOwnedBoards` reads `proposal_boards` where `project_id` is set; `useProjectBoards` reads `project_boards` (frozen). Near-identical hook names, two different tables, two different lifecycle states — and `useUpsertBoard`'s insert path targets `proposal_boards` for both owner kinds, which is exactly the surface class where IA-2's mistake recurs. → Not a UI fix, but a standing trap for the next feature; worth a naming/architecture note for implementers.

**IA-10 | P3 | confidence high | Acceptance-coverage gap | new** — The only "project-owned board write" acceptance evidence (AC1.29, Passed) exercises editing/renaming an EXISTING project board via the room, never creating one through `BoardsBuilder`'s blank/template picker. No AC among the 85 targets the New-board dialog against a project owner specifically — the ledger being fully green would not have caught F1/IA-2. → Add an AC exercising the picker's blank leg against a project owner.

**IA-11 | P3 | confidence low (expert judgment, unverified) | Procurement-spine tie-in** — Unclear whether a rejected board-pin verdict has an escalate-to-Decision path analogous to the FF&E schedule's C4 (`openComposeDecision` in `drafting-room.tsx`). Nothing in this lens's required reads shows a board-room equivalent of `ComposeDecisionSheet`. If board verdicts dead-end at "rejected" with no promotion into the Decision system, that's a spine gap. → Confirm with whoever read `board-verdicts.ts`/the client verdict flow directly.

**IA-12 | P2 | confidence medium (partial evidence) | Findability | new** — `navigation.ts` exports only `recentBoardCommandDescriptor` (existing boards) and `boardRoomHref`; no board-creation command constructor is visible from this module. I did not read `command-bar.tsx` itself, so this is inferred from the navigation helper's surface, not confirmed absence. → If ⌘K truly has no "start a new board" command, that's a fourth inconsistent entry point given how central ⌘K already is per Ruling #1.

## What's already excellent
- `project-boards-view.tsx` / `project-mood-boards.tsx`: genuinely legible "Working boards" vs "Signed direction" split with idempotent, busy-stated "Continue in project" — protect this pattern.
- `materialize_board_template` RPC: the one creation path that got the proposal/project owner split correct server-side — should be the template for fixing IA-2.
- `boardRoomHref`/`safeMoodBoardReturnPath` (`navigation.ts`): a careful allow-listed return-path contract (no open redirect) with consistent `source` attribution across all entry surfaces.
- One canonical full-viewport room (`/board/[boardId]`) that every owner kind and entry surface converges on — real architectural discipline despite the write-path bugs sitting underneath it.
- Consistent, centralized open-source taxonomy (`drafting_strip | desk_recents | command_bar | project_surface | direct_url`) feeding both navigation and analytics from one module.
