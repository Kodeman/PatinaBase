The scan bundle lands in Storage, then scan-pipeline runs ingest → solve → drawings and writes a versioned Room File. Three side lanes derive portal-facing assets from the same bundle; a parked COLMAP engine sits fail‑closed and unused.

solve fits scale against typed scan_anchors; every dimension is classed verified / measured / estimated. drawings emits a plan plus four elevations, each as SVG, PDF, and DXF R2010.

On the portal today: an SVG plan, a synthetic three.js Orbit that loads no real model, and photos. Room File sheets are downloads only.

Defect

The client portal still ships the react-three-fiber viewer with no scan-specific fallback — no ErrorBoundary/ScanStill degrade like the designer portal’s — so a crash falls through to the route’s generic error page.

agent_tasks remains the single queue. Ingest fans out — it does not chain. solve → verify → drawings is Lane C’s serial run, split across the CPU box and Modal; splat (Phase B) runs on Modal L4. Modal is a spawn target, reached via a billing‑guarded dispatcher that claims verify/splat/renders tasks and POSTs to a bearer‑secret Modal fastapi_endpoint, which .spawn()s the function (Modal web endpoints cap at 150s). Writeback runs over direct Postgres via a new least‑privilege scan_worker role — never service_role. There is no scan_pipeline.model stage — GLB optimization happens inside the conversion endpoint, not the queue. renders is enqueued by the edge function once a GLB lands, or by splat on a Phase B refresh; a drawings failure never blocks it, and vice versa.

PROPOSAL P1 portal work — GLB optimize, ModelStage, inline SVG — proceeds in parallel and is storage‑agnostic: it does not wait on the R2 pilot waves.

The outside spec answered “how do we build scan‑to‑CAD from nothing.” Our question was “how does the pipeline we already shipped grow into the full record of the room.” This is that answer.
