The Problem We Must Solve

Powerful tools can scare new users.

Every feature we ship makes Patina more capable — and potentially more intimidating. A first-time designer sees the Pipeline, the Aesthete Engine, the FF&E procurement pipeline, the Decisions module, the Change Order flow, and the Financial tracker before they've designed a single room. Without thoughtful guidance, capability becomes anxiety.

◐
Cognitive load
Eight new screens in the Designer Portal MVP. Each has 10+ properties. Designers cannot hold all of this in working memory.
◑
First-use uncertainty
"What do I do first?" is the most expensive question we can leave unanswered. Every minute of confusion in the first session predicts churn.
◒
Cross-portal complexity
Designers move between consumer app, Designer Portal, and Manufacturer Portal. Each has its own vocabulary, structure, and rhythm.

The goal is not a help center. The goal is a platform that feels like it was built with the user in mind at every step — where the right answer is visible at the moment the question forms.

Design Philosophy

Guidance is part of the product.

Help isn't an afterthought bolted onto the side of the interface. It's not a help center hidden behind a question mark icon. The help system is woven into the product itself — the empty states teach, the field labels reassure, the first-time experience guides without nagging, and the tooltips appear only when curiosity demands them.

"The best help is invisible. The user gets to the right answer without realizing they needed help at all."
Guidance System Principle

What this is NOT

NoA separate help center that requires leaving the workflow
NoForced video tutorials before the user can do anything
NoPersistent chat bubbles that interrupt focused work
NoMarketing-style "welcome to Patina!" modals
NoGeneric FAQs that don't know what screen you're on

YesEmpty states that teach what's possible
YesA guided first project that walks the designer through reality, not a tutorial

Five Guiding Principles

The rules that shape every help moment.

Every guidance decision — every tooltip, every empty state, every coachmark — gets measured against these five principles. They are the same principles that govern the rest of the design system: typography-first, document-metaphor, progressive weight.

01
Principle One
Contextual, not central
Help lives where the question forms. The Aesthete Engine question gets answered on the Aesthete Engine screen — not in a separate documentation site.
02
Principle Two
Progressive disclosure
Show the minimum first. Reveal depth when the user reaches for it. The wizard's "advanced" toggle. The tooltip's "Learn more" link.
03
Principle Three
Confidence over completeness
A user who feels confident takes the next action. We optimize for "I know what to do next," not "I now have all the information."
04
Principle Four
Quiet by default
No animated pop-ups, no badges, no badges-on-badges. Guidance whispers, never shouts. Pearl backgrounds, Clay accents, never Terracotta.
05
Principle Five
Earn the user's trust
Every help moment must prove its worth. If a tooltip isn't useful, it gets removed. We measure what gets read and what gets dismissed.
Underlying Goal
Make designers feel like the platform is on their side
Not a tool that requires expertise to operate. A collaborator that adapts to expertise as it grows.

System Architecture

Four layers of woven guidance.

The system has four layers. Each handles a different level of user need, from the casual scan-and-go to the deeply-stuck. Together they form a complete net — most questions never reach the next layer because the previous one caught them.

01
Ambient Layer · Always present, never intrusive
The interface itself teaches through clear labels, smart defaults, empty states, microcopy, and structural hierarchy. This layer carries 70% of the work. If a user has to think about what a button does, the button is failing.
02
Reactive Layer · Appears when summoned
Tooltips on hover, inline help text below complex fields, "Learn more" links that expand sections in place. The user pulls help toward them; it never pushes. Triggered by curiosity, not by the system's assumption that you need it.
03
Proactive Layer · Triggered by context
First-run experience, contextual coachmarks when a new feature ships, gentle nudges when a workflow appears stuck. The system reaches out only when it has high confidence that help is wanted — and always offers a "dismiss forever" option.
04
Reference Layer · For deep dives
The Help Center, accessible from the utility bar. Searchable articles, video walkthroughs, troubleshooting guides. The last-resort layer — most users should rarely reach it because the first three are doing their job.

Layer 1 · Ambient

The interface that teaches itself.

This layer carries the heaviest load. It is invisible help — guidance baked into the interface so completely that users never think of it as help at all. Strong field labels, sensible defaults, empty states that show what's possible, and microcopy that anticipates the next question.

Smart defaults

Every form ships with sensible defaults already in place. The 3% contingency. The six-phase template. The 15% product markup. The user can override any of them — but never has to start from zero.

Contingency Percent
Industry standard. Adjustable.

Empty states as onboarding

An empty Pipeline is the first thing a new designer sees. Instead of a sad "No projects yet" message, it becomes the entry point — explaining what the screen is, showing where projects come from, and offering the next action.

Microcopy that anticipates

Help text beneath fields answers the unspoken question. "Visible to client" or "Internal only" or "Affects FF&E recommendations." The user doesn't have to wonder what the consequence of a choice is.

Project Name *
Visible to client. Use clear, descriptive language they'll recognize.

Structural hierarchy

Typography-first design is itself a guidance system. Where the user looks first is where the most important action is. The Strata Mark guides the eye through stages. Required-versus-optional is visually obvious before reading a single field.

Visual hierarchy at workSection headers use Playfair Display 500. Field labels use DM Mono in Aged Oak. Required markers use Terracotta. Optional fields use italic Inter in Aged Oak. The user reads the form's importance before reading its contents.

Layer 2 · Reactive

Help on hover, not on push.

When a user is curious about something, the answer should be one micro-interaction away. Hover for a tooltip. Click an info icon for a deeper explanation. Expand a "Learn more" link to read the full context. Never demanding attention, always available.

Tooltip · The 2-second answer

Hover reveals a 1–2 sentence explanation. Disappears the moment the user moves on. No persistent UI element. The "○" indicator is small and unobtrusive — Pearl color, 12px size.

What this means An 87 means this client's style profile aligns strongly with your design vocabulary. Higher scores indicate easier collaboration and faster decisions.

Inline help · The "Learn more" pattern

A short hint, with a link to expand. The expansion happens in place — no modal, no navigation away. Returns to collapsed state after reading. Used for concepts that need a paragraph or two to explain.

The Strata Mark info icon

Patina-specific concepts (Aesthete Engine, Strata Mark, Founding Circle, the eight FF&E stages) deserve their own visual treatment. A small Strata Mark icon next to the term opens a contextual definition.

Reserved for Patina vocabularyThe standard "?" handles general questions. The Strata Mark icon handles "what's a Patina-specific thing." This distinction trains the user to recognize platform concepts immediately.

Contextual examples

For complex fields, the help text shows an example rather than a definition. "Type a project name" is unhelpful. "Try 'Chen Residence — Living & Dining'" is instantly understandable. Examples teach pattern-matching.

Example over definition"Project Name" gets the helper "Visible to client. Try 'Chen Residence — Living & Dining'." The user now knows: visibility consequence + naming pattern + acceptable format — without ever reading a rule.

Layer 3 · Proactive

The first-run experience.

The only time the system initiates is when a new user is meeting Patina for the first time, or when a major new feature ships. Even then, every nudge is dismissible, deferred, and limited to two or three moments. This layer earns its place by being rare.

The First Project Walkthrough

Instead of a tutorial, designers create a real first project — guided by spotlights and coachmarks that explain what they're seeing as they do it. The output is an actual project they keep. The teaching happens in the doing.

Feature announcement coachmarks

When we ship something new, returning users see a single, contextual coachmark next to the new feature. Dismissible. Never blocks the interface. Tracks per-user so it shows once and stays gone.

Rules for proactive moments
• Maximum 5 coachmarks per onboarding
• Maximum 1 coachmark per new feature release
• "Skip tour" always visible
• Dismissed = permanently dismissed
• Never blocks the underlying interface
• Never shown to users who completed the prior tour

Building Confidence, Not Just Competence

The emotional side of guidance.

Knowing how to use Patina is one thing. Feeling good about using it is another. Confidence is what turns a curious designer into a committed one. The system has explicit confidence-building patterns that go beyond just answering "how."

Confirmation moments

Every major action — activating a project, sending a proposal, approving a change order — has a brief celebratory confirmation. Strata Mark prominent. Sage success indicator. A clear "what just happened" summary. The Confirmation screen from project activation is the template.

Why this matters Confidence comes from receipts. "I did the thing, the system confirmed, here is what now exists." Without that loop, users second-guess themselves.

Progress visibility

Wizards show step indicators. Projects show phase indicators. The Aesthete Engine shows teaching progress. Wherever a user is making forward motion, that motion is visible. The Strata Mark itself is a progress symbol — bars of decreasing width that show momentum.

Visual progress = emotional progress Designers who can see how far they've come are 4× more likely to finish a workflow than designers who can't. (Industry research on multi-step form completion.)

Reversibility & undo

Most actions in Patina are reversible — and the system says so explicitly. "You can change this later in Project Detail." "This won't be sent until you click Send." Reducing the consequence of any single action reduces the anxiety of making it.

Confidence pattern When an action is irreversible (activation, sending an invoice, signing a change order), the system says so with equal clarity. Surprises kill trust.

The "save and resume" promise

Every wizard, every form, every multi-step flow auto-saves. The user can leave at any moment and return without losing work. This single feature, more than any tooltip, makes the platform feel safe to explore.

The safety net "Auto-saved 2 seconds ago" appears subtly in every wizard. Drafts persist 30 days. Resumable from any device. The fear of losing work disappears.

Guidance for Three Personas

The same system, three experiences.

Patina serves designers (Leah), makers/manufacturers (Sawkille, Nordic Atelier), and consumers (the iOS app users). Each persona needs the same guidance architecture, but the content and tone differ. The system adapts.

Designer · Leah

Professional partner

Tone: respectful of expertise. Help language assumes industry knowledge but explains Patina-specific concepts. Empty states encourage exploration. Tooltips define Patina vocabulary, not interior-design vocabulary.

"The Aesthete Score measures alignment between your design vocabulary and the client's style profile."

Maker · Sawkille

Production-focused

Tone: efficient, no fluff. Makers want to update an order status and move on. Help text is shorter, more action-oriented. Empty states focus on the next operational step, not concept explanation.

"Update PO #SK-087 to Shipped. Designer Leah will be notified automatically."

Consumer · iOS app

Warm and inviting

Tone: aspirational, conversational. Consumers are not industry professionals. Empty states tell a story ("Your style is forming"). Tooltips translate industry concepts into everyday language.

"As you save pieces you love, we learn what makes you feel at home. That's how we find your designer."

Shared System, Different Voice

The four-layer architecture is universal. The visual treatment is consistent — same typography, same Strata Mark, same Pearl-and-Clay palette. What changes is the voice. The system surfaces help in the same places, but writes it differently per persona. This is achieved through a centralized content management layer where copy is scoped to persona context.

How We'll Know It's Working

Help should make itself obsolete.

A well-designed guidance system improves the underlying product. When users repeatedly hit the same tooltip, that's a sign the interface needs to be clearer — not that the tooltip needs more words. We measure where help is used, not just whether it exists.

Target
90%
First project activated without help center visit
Target
<5%
First-run tour skip rate (sign of irrelevance)
Target
>4.5
"How easy was that?" rating on key flows (5-pt scale)
Target
<2%
Support tickets per active user per month

The four signals we watch

Signal 1Help searches per user. Climbing? The product has a comprehension problem. Falling? Either guidance is working — or users are giving up. Look at completion rates to disambiguate.
Signal 2Tooltip hover rates. Tooltips with high hover-and-dismiss rates need to be promoted into the interface itself. Tooltips with low hover rates may be unnecessary.
Signal 3Wizard abandonment per step. If 40% of designers abandon the Activation Wizard at Step 4, something about Step 4 is broken. Help is a symptom; the wizard is the disease.
Signal 4Direct feedback. Every help article has thumbs up/down + open comment. Sentiment shifts surface here first. Surveyed at 7-day and 30-day marks.

Content Governance

One source of truth.

Help content lives in one place — a structured CMS keyed to product surfaces. When the FF&E pipeline gains a ninth stage (someday), every tooltip, every help article, every empty state about that pipeline updates from one edit. No content drift, no outdated screenshots, no broken vocabulary across portals.

The architecture

ContentSanity CMS stores all help content — tooltips, helper text, empty states, articles, video metadata. Versioned. Editorial workflow before publish.
TargetingSurface keys identify which screen, persona, and component a piece of content belongs to. The frontend fetches by key — content is never hardcoded.
LocalizationFuture-ready for translation. English at launch. Spanish for Spanish-speaking field workers. Sanity's i18n structure ready from day one.
AnalyticsEvery help moment is tracked. Which tooltips get hovered, which articles get opened, which empty-state CTAs get clicked. PostHog dashboard for editors.

The writing standards

VoiceWarm but precise. "Visible to client" not "User-facing." "Send" not "Submit." Match the designer's professional vocabulary.
LengthTooltips: 1–2 sentences. Helper text: under 18 words. Articles: under 600 words. If a thing can't be explained briefly, the product likely needs simplification.
ExamplesShow, don't just tell. Wherever possible, lead with an example. "Try 'Chen Residence — Living & Dining'" beats "Type a project name."
ConsistencyCapitalized terms only when proper nouns. "Aesthete Engine" is capitalized. "the pipeline" is not. "Strata Mark" is capitalized. Consistent vocabulary across all surfaces.
Editorial responsibility Leah, as the design authority, has final approval on tone and vocabulary. The dev team flags features that need help content. A content designer (eventually) writes and maintains. PostHog data informs what to revise. Quarterly content audit.

Rollout Plan

Three phases, twelve weeks.

The guidance system rolls out alongside the Designer Portal MVP additions. Each phase delivers usable improvements — we don't ship a guidance system separately from the product it supports. By end of Sprint 3, all four layers are live across all three portals.

Phase 1 · Weeks 1–4

Foundation

• Ambient Layer audit across existing portal
• Smart defaults reviewed and confirmed
• Empty states rewritten
• Microcopy revised against new voice guide
• Sanity CMS schema for help content
• Surface key architecture established
Phase 2 · Weeks 5–8

Reactive Layer

• Tooltip component built and themed
• Helper text patterns applied to all forms
• Inline "Learn more" expandables
• Strata Mark info icon for Patina concepts
• First 40 help articles written and indexed
• Contextual help panel (utility bar "?")
Phase 3 · Weeks 9–12

Proactive & Reference

• First Project Walkthrough (5 coachmarks)
• Feature announcement coachmark system
• Full Help Center launch (search, browse)
• Video walkthroughs (first 10)
• Analytics dashboard live
• Pilot launch with Leah + 2 designers

Post-launch · Continuous

Quarterly content audit Every quarter, review tooltip hover rates, article views, support ticket themes. Retire what's not working. Strengthen what is. Add help for new features at ship-time.
User feedback loops 7-day and 30-day surveys for new designers. Thumbs up/down on every help article. Open comment field on the help panel. Direct feedback channel to the content designer.
