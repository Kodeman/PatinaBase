v1 Scope · What Changed From the Concept

Six decisions sharpened the build.

The original concept proposal raised six refinement questions for the Patina team. Each answer ruled out a path. The collective effect is a tighter v1 that ships faster and serves Leah's actual workflow more precisely than the original concept would have.

Decision 1 · Receiving
Leah receives on her own — at her studio.
Receiving view becomes phone-first from day one, not Phase 2. Optimized for "3 photos, 2 taps, done" rather than third-party receiver documentation. Partner portal drops from v1 entirely.
Decision 2 · Payments
Payments track inside the workspace.
Vendor payment terms vary — 50/50, 30/70, milestone, NET-30. Payment state lives as a sub-flow on each PO, surfaced in By Vendor and By Status views. Not a separate finance module. See companion doc for the model.
Decision 3 · Calendar
Project-axis only. No vendor calendar.
Calendar shows deliveries and installs organized by project. Logistics conflict detection (overlapping arrivals, install-after-delivery sequencing) still runs. Vendor-as-axis dropped — not useful at solo-designer scale.
Decision 4 · Vendor entity
Company-level only. Contacts are notes.
"Sawkille Co" is the record. Person-level contact info attaches as a note on the vendor record. Cuts data model complexity and matches how a solo designer actually thinks about it.
Decision 5 · ETA tracking
Manual updates only in v1.
Designer updates ETAs through quick-edit when vendor emails arrive. Email parsing and automated ETA capture defer to v2 once we have data on which vendors send predictable confirmation formats.
Decision 6 · Bookkeeper
QuickBooks-ready CSV export. No new user role.
A single filtered export screen produces a CSV the bookkeeper imports into QuickBooks. No login for them, no permissions matrix to design. See companion doc for column mapping.

What ships, what waits.

v1 ships what Leah needs to make Order Day, Status Tuesday, and Install Week dramatically less painful. v2 expands integrations, automations, and partner-facing surfaces. The boundary is deliberate: build the human-centered foundation first, layer automation on top once we have real usage data.

Payment tracking · Model overview

Vendor terms are the spine.

v1 confirmed: payment tracking lives inside the workspace, not as a separate finance module. Each vendor defines default terms. Each PO inherits and can override. Payment state lives as a parallel track to the 8-stage procurement pipeline, with automatic action surfacing at key stage transitions. The full data model and field-level spec is in the companion document.

Five supported payment patterns in v1

50/50Deposit on order, balance before ship. Most common for custom furniture.
30/70Lower deposit, larger balance before ship. Some manufacturers prefer this for cash flow.
100% upfrontFull payment at order. Common for small custom items, antique purchases, in-stock retail.
NET-30Full payment 30 days after delivery. Trade accounts with established vendors.
Custom milestones2–4 payment events with custom amounts and trigger conditions. Complex custom work.

How payment state connects to procurement state

Approved → No payment activity yet.
Ordered → Deposit becomes due. Pill: "Deposit $X due [date]."
Deposit paid → Logged with date. Pill flips to "Deposit paid."
Production → Balance pre-stages but not yet due.
Shipped → Balance becomes due. Pill: "Balance $X due [date]."
Balance paid → Logged. Pill flips to "Paid in full."
Delivered → NET-30 vendors: balance due-date sets.
Installed → Final reconciliation only.

Payment state never blocks procurement state. Leah can advance an item to "Shipped" before paying the balance — the system just flags the balance as due. She controls when to pay.

"Payments don't live in their own world. They live alongside the items they're paying for. The same screen where Leah sees 'Meadow Linen Sectional is shipping next week' shows her 'balance $3,400 is due before that.' One workflow. One source of truth."

Rollout · v1 build plan

Three sprints. Twelve weeks to pilot.

The build plan reorganizes around the v1 scope decisions. Phase 1 ships the highest-value views (By Vendor, By Status, payment tracking). Phase 2 adds Calendar and the mobile Receiving flow. Phase 3 closes the loop with bookkeeper export and capture integration.

Phase 1 · Weeks 1–4

Order day, financial truth

• New Procurement zone in top nav
• By Vendor view with grouping logic
• Order Assistant side panel
• One-click Patina Catalog ordering
• Vendor entity (company-level) data model
• Payment terms model + payment state on POs
• By Status view with payment pills
• Project Detail FF&E zone collapsed to summary
Phase 2 · Weeks 5–8

Logistics, mobile inspection

• Calendar view (project-axis)
• Automated conflict detection
• Receiving desktop view (dashboard)
• Mobile receiving flow (iOS first)
• Damage claim auto-draft
• Today Dashboard procurement card
• Manual ETA quick-edit UX
Phase 3 · Weeks 9–12

Bookkeeper, capture loop

• Bookkeeper QuickBooks CSV export
• Studio owner permissions
• Capture-to-slot integration (5-sec capture)
• Layer 1 → Layer 2 promotion flow
• Layer 2 → Layer 3 nomination flow
• Notifications model
• Pilot launch with Leah + 2 designers
What we measure

Order-day duration: target 60% reduction. Damage discovery lag: under 48 hours. Payment status accuracy: 100% of POs have payment state visible without manual reconstruction. Bookkeeper handoff time: minutes, not hours. Calendar conflicts prevented: count of issues caught before becoming logistics emergencies.

After v1 · Documented for the future

What we defer, and why.

The deferred features aren't forgotten — they're documented as v2 candidates with a clear trigger condition. Each one waits for evidence from v1 usage that the additional complexity is worth the build effort.

QuickBooks Online API integration
Trigger: Pilot bookkeepers report CSV reformatting taking longer than 15 minutes per export. Or pilot scales to 10+ designers and CSV manual import becomes a bottleneck.
Automated ETA email parsing
Trigger: Analysis of manual ETA updates shows 70%+ come from a small set of vendors with predictable email formats. Email connector becomes ROI-positive.
3rd-party receiver partner portal
Trigger: Designer pilot expands beyond solo practitioners into studios using professional receivers (Hilldrup, Designers Warehouse). Partner portal requires onboarding flow + permissions model.
Vendor person-level contact records
Trigger: Multi-designer studios start sharing vendor relationships and need to track which person at the vendor each designer works with. Solo Leah doesn't need this.
Vendor calendar axis
Trigger: Studios manage 20+ active vendors with frequent crossover. Vendor-axis becomes useful for "what's happening with Sawkille this month across everything."
Client payment ↔ vendor payment linkage
Trigger: Pilot feedback identifies repeated friction around "the client paid me on Friday, I need to pay Sawkille on Monday — when do I know it's safe to release the balance?" Requires designing the cash-flow view.

Each deferred feature has its own future spec document waiting. v1 ships fast and lean. v2 expands based on what pilot teaches us — not on what we guessed at the start.
