Contents

Twelve screens, three entry paths.

A new project starts in one of three ways: convert from a signed proposal (the common path), start blank (rare — for projects that never had a proposal), or duplicate from template (for repeat work patterns). All three converge on the same wizard and produce the same data.

Path A · From Proposal
Most common. Click "Activate Project" on a signed proposal. 80% of fields pre-fill. Designer confirms, adjusts, and activates.
Path B · Start Blank
For projects that bypassed the proposal builder (legacy clients, referral work). Designer enters all data manually.
Path C · Duplicate
Copy from an existing project or saved template. Useful for repeat work like model unit packages or annual refreshes.

The Wizard · 7 Steps

From confirmation to activation.

Once a path is chosen, the wizard takes over. Seven sequential steps, each with auto-save, each able to be skipped or revisited. The wizard sits in a focused-mode view (no main navigation visible — the Strata Mark replaces the logo) to signal that the designer is mid-flow.

Implementation Summary

From entry to activation.

Total properties documented

Across the 12 screens, this document specifies 113 distinct properties with type definitions, requirement levels, default behaviors, and validation rules. Every property maps to a database field, an API parameter, or a UI behavior.

Required vs. Optional

Approximately 40% required, 35% optional, 25% auto-computed. The high auto-computed ratio reflects the from-proposal flow — most fields are filled by data already in the system, not asked of the designer again.

Auto-save behavior

Every wizard step auto-saves on field blur. Drafts persist 30 days. Designers can leave any step and return — including across sessions, devices, and after browser crashes. The wizard state is tracked separately from the project record itself, so an incomplete draft never appears in the active pipeline.

Time to activation

Target: 15 minutes for from-proposal flow, 30 minutes for blank flow. Pilot designers will measure actual times to validate. If steps consistently exceed these targets, the wizard gets re-evaluated.
