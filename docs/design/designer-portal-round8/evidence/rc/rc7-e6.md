## WebKit /desk interruption (harness, not a product defect)

W1/W2 failed with `page.goto: Navigation to "http://localhost:3610/people" is interrupted by another navigation to "http://localhost:3610/desk"`. `f18a5aa3b` retries only that exact error. Static root cause, before Phase 2 instrumentation:

- **Not a sign-in double navigation.** `src/app/auth/signin/page.tsx:80–84` schedules the 350 ms `window.location.replace(destination)` inside an effect whose cleanup clears the timer. The timer lives in the sign-in document, so a document load of `/desk` destroys it, and a soft navigation to `/desk` unmounts `SignInContent` and clears it. Nothing on the password path re-requests `/auth/*` or `/` after sign-in: the form calls `preventDefault` (`PortalAuth.tsx:576`) and there is no `router.refresh`/`router.push`. So the authenticated-auth-page redirect (`src/middleware.ts:164–175`) cannot land on `/desk` while that timer is pending. `/desk` (`src/app/(document)/desk/page.tsx`) issues no navigation on mount, and `/people` has no redirect to `/desk` in `next.config` or in the middleware.
- **Cause: the Next dev server reloads the open `/desk` document.** `playwright.round8.config.ts:42,45` starts a fresh `next dev --webpack` for each run, so routes compile on demand. Every logged maker run (C1, C2, W1, W2, W3, W4, C3, C4) prints exactly one `[WebServer] ⚠ Fast Refresh had to perform a full reload` immediately before the maker result line. While `/people` compiles, the open `/desk` document's HMR client cannot apply the update and calls `location.reload()`. WebKit lets that renderer-initiated `/desk` reload pre-empt Playwright's provisional `goto('/people')`; Chromium keeps the browser-initiated navigation. This is dev-only: production builds ship no HMR client.
- **Instrumentation for Phase 2.** `rc7-e6-maker.spec.ts` extends `page` before the auth fixture runs, logging main-frame `framenavigated` paths and browser `Fast Refresh`/`full reload` console lines with ms offsets. It also sets `peopleRecoveryFired` in the catch branch. Both are emitted as the `e6-nav-log` and `e6-people-recovery` annotations and as stdout lines `[e6-nav-log]` and `[e6-people-recovery]`. The prediction to test: when the recovery fires, the log shows a `/desk` navigation after `goto /people start`, next to a full-reload console line.
- Side note, not a defect: `PortalAuthSuccess` (`PortalAuth.tsx`) renders `<a href={destinationHref} onClick={onContinue}>` without `preventDefault`. A user click therefore issues `location.replace` plus the anchor navigation, both to the same destination. The automatic path never clicks it.
