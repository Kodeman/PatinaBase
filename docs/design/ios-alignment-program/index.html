01 The Situation

One company is shipping two brands.

Both iOS apps are built by the same team, on the same backend, for the same designers and clients. One looks unmistakably like Patina. The other looks like a competitor. Neither is finished. The good news buried under all of it: the work ahead is assembly, not invention.

I.

Patina Field is off-brand by design.

The July app split gave Field a deliberate "field instrument" identity — verdigris, brass, rust; Fraunces / Hanken Grotesk / IBM Plex Mono; light-only. It is internally disciplined: lint-enforced tokens, Dynamic Type throughout. The engine is strong; the brand is wrong. Nothing is shared with the client app — no common package, hand-synced ports for QR auth and media upload, and roughly 900 color call sites living on a fork.

II.

The Patina client app is on-brand but rail-less.

Its tokens are the exact canonical hexes; dark mode and 14 shared components already exist. But there is no persistent navigation shell. ProjectListView, ThreadListView and DecisionListView are fully built, wired to live Supabase data — and reachable only when a push notification happens to arrive. The app also has zero transactional surface: no proposals, invoices, payments, budget or documents, all of which the client web portal ships today.

III.

The backend is already done.

Every feature this program adds to the client app mirrors an existing client-portal surface — same tables, same RPCs, same edge functions, all RLS-tested in production. No new migrations are expected. This is an assembly program, not an invention program.

Scope — already ruled by Kody

Studio railwireframe · Patina tokens · not a build

Recommendation (ask R29): a "Studio" hub rail on the DailyRoom home — not a tab bar.

The architecture argues for it. The app is a single NavigationStack + coordinator + companion-overlay. A TabView retrofit re-plumbs all of that; a home-hub rail rides the structure that already exists.

The Document argues for it. Its language is typography-first hubs — a Playfair title, DM Mono meta and a count badge per row — not chrome.

The data argues for it. There are only ~2 real top-level destinations today. The tab-bar question is properly re-asked after the transactional rail exists — a post-Track-D review clause.

Badge counts come from a BadgeCountService — pending client_decisions + unread comms, mirroring the portal's use-inbox queries — refreshing on foreground and push. Realtime only if publication membership verifies; otherwise it polls, so a correct floor is always guaranteed. Companion quick-actions and profile rows stay as secondary entries.

What this section meansOne ruling: R29 — build the rail now, revisit the tab bar after the money rail ships and real usage exists.

08 Where This Bites

Nine risks, each with a defense.

RISK 01
pbxproj regeneration collisions

Parallel Field component waves each add and remove project files.

DefenseFile adds / removes funneled through one integrator; merges serialized.
RISK 02
Verdigris blanket-remap green-brands Field

A single mapping paints the whole app green.

DefenseR28 split-classification happens before the value flip.
RISK 03
CaptureKit freeze vs. the design swap

The kit is meant to be frozen; the swap touches its color / type surface.

DefenseCaptureColor / CaptureType stay API-stable aliases; freeze exemption documented.
RISK 04
Token-ratchet baselines shift under big diffs

Large sweeps move the raw-usage counts the ratchet guards.

DefenseRe-baseline only in B.3, never mid-wave.
RISK 05
Apple reviewer friction on external payments

Web-payment handoffs draw scrutiny.

DefenseClear web handoff, 3.1.3(e) rationale in the review notes.
RISK 06
Boards-fidelity rabbit hole

Proposal boards tempt a full canvas rebuild.

DefenseThumbnails only; the canvas is backlog.
RISK 07
Realtime badge counts unverified

Publication membership for live counts isn't confirmed.

DefensePoll-on-foreground floor; a publication add would be migration 00285+.
RISK 08
.dynamic SPM product in a generated project

The least-trodden Xcode-generation path.

DefenseWave 0 proves it on device; fallback pre-agreed in R27.
RISK 09
ACH settles slowly

Payments can sit pending for days.

DefensePending-state copy sets expectations; the portal already models this.
What this section meansTwo of these defenses are themselves rulings — R28 (the split before the flip) and the R27 fallback (verbatim port if the package path resists). Nothing here starts before Wave 0 proves the kit.
