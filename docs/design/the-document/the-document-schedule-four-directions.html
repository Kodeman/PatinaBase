The problem it solves

Truncated labels, an invisible today, a dishonest sequence — fixed in place, without asking the page to change around it.

How it works

One full-width rule. Labels sit above at natural width, staggered when they'd collide — nothing ever truncates. Weight encodes status: light for closed, bold for active, muted for ahead. Milestones are diamonds on the line. Procurement — the perpetual overlapper — runs as its own hairline beneath, spanning its true dates. Click any phase and it unfolds inline.

Where it lives

Drop-in replacement for the current bar. Same position, same footprint, same "unfold" language as the rest of the Document.

The tradeoff

Still a summary strip. It points at problems; it doesn't hold them. The work stays estranged from the schedule, just better introduced.

The vision

The schedule as a ruled line in a ledger — the one instrument on the page that behaves like it was drawn by hand.

The problem it solves

The disconnection problem — schedule up top, work down below, nothing between them. Here they become the same object: the sign-off holding the line lives inside the phase it's holding.

How it works

A vertical spine down the left margin. Each phase is a heading; Coordination and The Work dissolve into it — sign-offs, punch items, FF&E lines each under the phase they belong to, ball-in-court chip inline. Closed phases compress to one light line. Today is a rule that crosses the spine. Procurement travels as a running thread rather than pretending to be sequential.

Where it lives

This is the project page's architecture, not its header. The most Document-native option — the project reads top to bottom like a story.

The tradeoff

You lose the compact glance strip — though Option A can serve as its collapsed header state — and the page gets longer.

The vision

The project reads top to bottom like a story — and the schedule is the spine of the book.

Blocked by a decision

The blocked sign-off, made visible: order the sofa today and its 12-week lead still delivers it 15 days after install begins. That golden dot is your "Do it" sign-off — physically holding the schedule hostage.

The problem it solves

The question every design-build project turns on — will the pieces land before install week — is invisible in every tool on the market. Lead times ARE the schedule; this is the first view that treats them that way.

How it works

A quiet time axis, one row per phase, bars in warm neutrals. Beneath: the thread layer — every FF&E line drawn from order to delivery. A thread landing after install begins turns Terracotta. A decision blocking an order is a Golden Hour dot. Drag a phase edge and the downstream ripple previews before you commit.

Where it lives

A Studio Eyes Only layer that unfolds on demand — you and the GC need the loom; the client doesn't. Pairs naturally under Option A or B.

The tradeoff

Densest option, wants horizontal room, biggest build. Highest payoff, highest cost — and it must be styled ruthlessly or it reads as engineering software.

The vision

Studio Designer and Houzz Pro both punt on this view. Built beautifully, it's a reason to switch.

Clients don't experience phases. They experience dates and signatures.

The problem it solves

Duration bars answer questions clients never ask. What they ask is: what's the next date, and whose signature does it need? The almanac is honest to how designers actually communicate.

How it works

Phases recede to muted context. The foreground is a curated ledger of commitments — decision points, sign-offs, deliveries, install day — each with a date, a name, and a stamp borrowed from the proposal's own language: Signed, Due, Slipped, Upcoming. The client view simply hides studio-only rows.

Where it lives

The client-facing projection of whatever runs the studio side. It can also headline the proposal — the timeline a client signs against.

The tradeoff

Weak at duration and overlap reasoning. Lives or dies on milestone curation — six entries is a story, twenty is clutter.

The vision

"Here are the six dates that matter — and whose signature each one needs."

A Possible Composition · These aren't mutually exclusive

Four options, four roles.

The strongest read of the field is a composition, echoing the strata themselves — but that's a roadmap, not a v1. V1 should be one thing, done completely.

DThe client projectionWhat the client sees — and signs againstOutward
AThe collapsed headerThe glance — the strip, fixed and honestSurface
BThe bonesThe page architecture — work dissolved into timeStructure
CThe studio layerThe loom — unfolds on demand, studio eyes onlyDepth

If v1 must be one thing: B if you're ready to restructure the project page around it. A if you want the strip fixed this sprint and the restructure earned later.

Three questions to shape your ruling
1

Whose instrument is v1?

Is the schedule primarily your instrument, or the client's window? The answer picks between the studio options (A, B, C) and the projection (D).

2

How much page are you willing to move?

Upgrade the strip in place, or restructure the project page around time? A is a component swap; B is an architecture ruling.

3

Do lead times need to be visible in v1?

Or is phase-and-milestone honesty enough for now, with the loom earned once real FF&E data flows?

Awaiting your ruling.
