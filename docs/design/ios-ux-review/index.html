01 Executive Summary

A beautiful instrument with broken strings.

Patina iOS has a design soul most apps never find — Playfair and clay, whisper bars, haptic milestones, a layered strata icon. The token system rivals the web portal's. But on a real device the experience contradicts the craft: the home screen's primary call-to-action does not respond to taps, decision options render with no content above an "Approve" button, several core screens are navigation dead ends, four Settings rows do nothing, and dark mode — fully designed in PatinaColors — is simply never used. The gap is not design vision. It is adoption, wiring, and finish.

02 The Two Journeys

One app, two lives: homeowner and designer.

The account we walked is dual-role. The consumer journey (scan → style → recommend → save) and the designer journey (projects → decisions → messages → receiving) share one navigation spine and one companion. Below, the actual screens as captured — annotated where the seams show.

03 Findings & Recommendations

Twenty-six fixes, in the order they hurt.

Each finding below was either reproduced on the device or verified in source. P0 = broken or trust-damaging, fix first. P1 = friction that erodes the experience. P2 = polish that compounds. Effort is sized S / M / L.

Theme I — ReachabilityButtons that don't work are promises broken.

The single most damaging pattern found: primary actions rendered as 15-pt static text, hit areas swallowed by neighbors or by the companion's gesture layer, and rows with chevrons that go nowhere. Users will not file bugs — they will conclude the app is broken and leave.

P0Device-verifiedEffort S
"Scan a room" — the home CTA — does not respond to taps

The app's most important button is an 88×15 pt StaticText with no button trait. Repeated taps at its center do nothing; the companion's pull-gesture overlay appears to swallow touches near the bottom edge. The flow only opens via the companion menu.

RecommendationMake it a real Button wrapped in PatinaButton (44 pt min target), and exclude the companion's gesture region from content hit-testing. Add a UI test that taps it.
P0Device-verifiedEffort S
"See recommendations" is unreachable by touch

On room detail the link sits 1 px above the full-width "Work with a Designer" button; every tap — even dead center — triggers the button instead. Recommendations, a core consumer promise, cannot be opened from a room.

RecommendationPromote it to a secondary PatinaButton in the action bar with its own 44 pt row; never stack a text link flush against a full-width button.
P0Device-verifiedEffort M
Four Settings rows are dead — including Account

Account, Style Preferences, Connected Portals, and Appearance all render with chevrons; none navigate. Account is the path to sign-out and profile management — likely a NavigationLink inside a sheet that has no NavigationStack, so it silently no-ops.

RecommendationWrap the Settings sheet in NavigationStack; remove or build the placeholder rows. A chevron is a contract — never ship one that does nothing. Features/Settings/Views/SettingsView.swift
P1Device-verifiedEffort S
Companion "Designer workspace" action goes nowhere

From the consumer home, tapping the companion's "Designer workspace — Projects · Decisions · Messages" row closes the menu and stays put. The header's switch-mode chip works; the companion intent doesn't.

RecommendationRoute the intent through the same AppCoordinator.handleIntent path the role chip uses, and add intent-coverage tests for every companion action.
P1Device-verifiedEffort S
Room items can't be opened

Item rows in a room ("Walnut Lounge Chair, $1,850") respond only via their overflow "More actions" button — tapping the row itself does nothing, so there is no path from an owned item to its product page.

RecommendationMake the whole row tappable → ProductDetailView; keep the overflow for move/copy/remove.
P2Device-verifiedEffort S
Room chips give no feedback

Tapping a room chip on home produces no visible change (it filters an empty rail). Selection state, if any, is imperceptible.

RecommendationShow selected state (filled chip), scroll to the rail, and when the rail is empty for that room, swap in a contextual empty state ("Nothing saved for Kitchen yet — scan or browse").

Theme II — WayfindingEvery screen needs a way back.

Decision detail, project detail, and the conversations list shipped with no back affordance and edge-swipe disabled; the style quiz cannot be exited at all. The companion becomes an accidental escape hatch — clever, but no substitute for navigation.

P0Device-verifiedEffort M
Designer screens are navigation dead ends

Decision detail and project detail render zero navigation controls — no back chevron, no toolbar, and interactive edge-swipe is disabled by the hidden navigation bar. The accessibility tree confirms: the only buttons on decision detail are three "Approve"s.

RecommendationStandardize a screen chrome: every pushed view gets the back chevron pattern already used on Profile and Notifications. Re-enable interactivePopGesture when hiding the bar.
P0Device-verifiedEffort S
The style quiz is a trap screen

Once opened, the quiz offers four answers and a progress bar — no close, no back, no skip. The only exits are answering all five questions or force-quitting the app.

RecommendationAdd an ✕ with a "Save progress & exit?" confirm. Persist partial answers so returning resumes at question N.
P1Device-verifiedEffort S
An orphaned overlay follows you across screens

After leaving room detail, its "See recommendations →" pill persisted on top of the Profile screen — a floating fragment of a previous screen's UI (state leak in the overlay layer).

RecommendationBind overlay pills to screen lifecycle (.onDisappear teardown) rather than the global overlay host; add a regression test.
P1Effort M
The companion is the de-facto tab bar — make wayfinding honest

With no tab bar, every cross-section jump routes through the companion. It's a distinctive idea, but today it's also masking missing navigation: users must discover that the floating dot is the menu.

RecommendationKeep the companion, but (a) give it a visible label on first sessions ("Menu"), (b) ensure every section is also reachable by conventional means (header buttons, back chevrons), and (c) instrument it — if >50% of navigation flows through it, consider a slim tab bar for Home / Spaces / Saved / Studio.

Theme III — The Decision MomentApproval needs evidence.

Decisions are Patina's highest-stakes interaction — money and taste change hands. On device, option cards rendered as the word "Option" above an Approve button: no title, no image, no price, no comparison. Whether data or rendering, the safeguard is the same: never let an approve button appear without content.

P0Device-verifiedEffort M
Decision options render without content

Option title falls back to the literal string "Option"; description, image, and price are absent. A client cannot tell what they're approving — and an approval here is contractual.

RecommendationRequire a minimum render contract: name + image-or-placeholder + price. If fields are missing, show "Details unavailable — view in portal" and disable Approve. Fix the data path from client_decisions options. Features/Decisions/Views/DecisionDetailView.swift
P1Effort S
Decisions lack project context and a discussion path

The inbox lists "Task lamp / Pendant scale" with no project name; detail offers approve-or-nothing. Web supports comments and clarification; iOS should not force a binary.

RecommendationAdd the project name + room to each row; add a "Discuss this" action on detail that deep-links into the project thread.

Theme IV — The Scan RitualProtect the magic moment.

The walk itself — whisper bar, haptic milestones, motion-triggered threshold — is the app's best work. The edges betray it: an empty "finish" silently created a room named Kitchen, the pause menu has no exit, and the review screen never appeared.

P1Device-verifiedEffort S
Empty scans finish silently — and still create a room

"Finish With What We Have" on a zero-data scan returned straight to home with no review, no message — and a new "Kitchen" room appeared in the chip rail. The user is never told anything happened.

RecommendationBelow a data threshold, disable Finish with an inline reason ("Walk a little more first"). Never create a room without showing the review step or a confirmation toast.
P1Device-verifiedEffort S
The pause menu can't abandon a scan

Paused offers Resume / Finish / Start Over. There is no "Exit without saving" — Start Over restarts the capture; leaving entirely means finishing or killing the app.

RecommendationAdd "Leave scan" with a discard confirm; route home via the coordinator.
P2Effort S
Motion-only start needs a fallback cue

The threshold auto-starts on motion — poetic, but a first-timer holding still sees a black screen with no instruction to move.

RecommendationIf no motion within ~5 s, fade in a whisper: "Begin walking to start" + a manual Start. Features/RoomScan/Views/ScanThresholdView.swift
P1Effort M
Upload failures are swallowed

From the code audit: scan upload errors log to PostHog and the UI proceeds regardless. Offline queueing exists (good); user-facing truth does not.

RecommendationSurface a quiet sync status on the room card ("Uploading… / Will retry when online") fed by RoomScanSyncService.

Theme V — Content IntegrityPlaceholders are showing.

Blank brown squares where product photos should be, gradient rectangles labeled "Which room speaks to you?", rooms rendered as anonymous swatches, raw enum strings on project cards. The brand sells material truth; the screens must too.

P1Device-verifiedEffort S
Failed images render as blank rectangles

Room items show flat brown squares; profile room cards show bare gradients; decision images fall to nothing. AsyncImage failure cases are unstyled across the app.

RecommendationOne shared PatinaAsyncImage with a branded failure state (strata mark on linen texture + retry on tap). Replace all raw AsyncImage uses.
P1Device-verifiedEffort S
Raw enums leak into the UI

Project cards and detail print design_development verbatim. The portal formats these; iOS must too.

RecommendationA PhaseDisplayName formatter mirroring the portal's vocabulary ("Design Development"), used everywhere a phase or status renders.
P1Device-verifiedEffort M
The quiz asks about rooms but shows none

"Which room speaks to you?" presents four flat gradient swatches. The question is unanswerable as posed — and this is the moment that seeds the style profile.

RecommendationShip four real room photographs per question (bundled assets, art-directed per aesthetic). If imagery isn't ready, rewrite the prompt to match swatches ("Which palette feels like home?").
P1Device-verifiedEffort M
Project detail is a stack of empty states

"No phases yet / No payment milestones yet / No FF&E items yet" — three grey shrugs and nothing else, for a project the list says is worth $48,000 in design development.

RecommendationLead with what exists (name, phase, budget, client, last activity); collapse absent sections into a single "Set up in the portal →" hint rather than three empties.
P2Device-verifiedEffort S
Home's lower half is dead air

Below the room chips: a filter row over an empty rail, then 350 points of nothing. The screen reads as unfinished on first launch.

RecommendationWhen the rail is empty, replace chips+void with one editorial module: tour card, quiz prompt, or maker story #2 — never bare filters.
P2Effort S
Hardcoded fallback copy

"Handcrafted by artisans in the Patina network" stands in for every missing product story; the share tooltip describes behavior that doesn't exist (share is a no-op in ProductDetailView).

RecommendationImplement share via ShareLink to the portal URL; vary fallback copy by maker/category or hide the section.

Theme VI — ConversationMessages deserve a shape.

Threads titled "Direct" with ISO timestamps; messages as undifferentiated stacked sentences — no bubbles, no senders, no time, no read state. For an app whose business is designer-client trust, the conversation surface is the relationship.

P1Device-verifiedEffort M
Message rendering lacks every chat affordance

No sender attribution, no left/right alignment, no timestamps, no grouping. Two parties' words are visually identical.

RecommendationStandard chat anatomy in Patina's voice: own messages right-aligned on clay, theirs on cream with sender name; day separators in DM Mono; relative timestamps. Features/Messaging/Views/ThreadDetailView.swift
P1Device-verifiedEffort S
Threads are unidentifiable from the list

Multiple rows titled "Direct"; no participant name, no last-message preview, no unread weight. VoiceOver reads raw ISO-8601 strings.

RecommendationTitle = counterpart's name (resolve from participants); subtitle = last message preview; trailing relative time; bold-on-unread. Format dates before they reach AX labels.

Theme VII — AccessibilityThe tree tells the truth.

Reading the live accessibility tree exposed what screenshots can't: overlays that leave the whole background screen tappable to VoiceOver, switches with no labels, the companion bubble absent from the tree entirely, and a typography system whose hardcoded sizes ignore Dynamic Type.

P0Device-verifiedEffort M
Overlays don't hide the screen beneath

With the story detail open, every home control — chips, bell, profile — remained in the AX tree as visible and enabled. VoiceOver users will tab through a ghost screen behind the content.

Recommendation.accessibilityHidden(true) on background content while any overlay/expanded card is presented; audit story, product, and companion overlays.
P1Device-verifiedEffort S
The companion is invisible to assistive tech

The floating bubble — the app's primary navigator — has no button trait and no label (an "Other" node, sometimes absent entirely). VoiceOver users cannot find the menu.

Recommendation.accessibilityElement() with label "Patina companion — menu", trait .button; verify the pull gesture has an AX action equivalent.
P1Device-verifiedEffort S
Unlabeled switches in Settings

The Notifications/Haptics toggles expose no AXLabel — VoiceOver announces "switch, on" with no subject.

RecommendationLabel every Toggle; add a lint/test pass asserting no interactive element ships label-less.
P1Effort L
Dynamic Type is effectively unsupported

Tokens use fixed sizes (7–56 pt, some off-scale like 11/13/21 pt) plus raw .system(size:) calls; accessibility text sizes change nothing. Inter-Light is referenced but not embedded — it silently falls back.

RecommendationRoute PatinaTypography through @ScaledMetric/relativeTo everywhere, kill raw .system(size:) in features, embed or remove Inter-Light. Test at AX1–AX5.

Theme VIII — System CohesionOne kit, used everywhere.

The token files are genuinely good — semantic colors with a warm dark palette, a full spacing/radius scale, five button styles. Features then hand-roll their own: 14 pt corners that exist in no scale, 9/10/20/28 pt padding, system fonts beside brand fonts, a dark-themed services sheet inside a light app.

P1Effort M
Token adoption pass

Off-grid spacing and radii across Home, Settings, product cards; DailyProductCard, ProductCard, RoomChipRail, SettingsView are the worst offenders.

RecommendationOne sweep: map every hardcoded value to PatinaSpacing/PatinaRadius (extend the scale where 14/20 pt is genuinely wanted). Add a danger-style grep check to CI.
P1Device-verifiedEffort S
The services sheet breaks theme

"Get Design Help" renders charcoal-on-dark inside an otherwise light app — the only dark surface, and not by design system intent.

RecommendationRestyle on Background.primary/PatinaCard; reserve dark surfaces for camera/AR contexts where they earn their keep.
P2Effort M
Button fragmentation

PatinaButton (capsule, 52 pt) coexists with AuthButton (12 pt corners, 50 pt), bespoke BackChevronButtons, and inline-styled buttons.

RecommendationFold OAuth + back-chevron variants into PatinaButton styles; deprecate the rest.
P2Effort M
Native patterns are missing where users expect them

No .searchable on lists, no .swipeActions (delete/archive), no .contextMenu on cards, pull-to-refresh inconsistent, no Reduce Motion checks.

RecommendationAdopt platform furniture deliberately: search on Conversations/Projects, swipe actions on saved items and notifications, context menus on product cards, accessibilityReduceMotion gates on the big animations.
04 The Dark Mode Spread

A dark palette exists. The app never calls it.

We flipped the device to Dark Appearance and re-shot the same screens: nothing changed. The app doesn't force light mode — PatinaColors.DarkPalette and the patinaDynamic() bridge are built and waiting — but features hardcode offWhite, softCream, and charcoal directly (~14 dynamic usages in the entire app). Tonight, every user who reads in dark mode gets a flashlight.

P0Device-verifiedEffort L
Adopt the semantic palette, screen by screen

Replace direct palette references with semantic roles — Background.primary, Text.primary, Interactive.* — which already resolve through patinaDynamic() to the warm-graphite dark set.

RecommendationPhase it: tokens are ready, so this is mechanical. Sequence: Home → Settings/Profile → Rooms → Designer → sheets. Until complete, declare UIUserInterfaceStyle = Light in Info.plist so mixed system components (alerts, share sheets) don't render half-dark against light screens.

06 The Master Plan

Three phases. Trust, then flow, then delight.

Sequenced so each phase ships a coherent, testable promise. Phase 1 is almost entirely small/medium tickets — a focused two-week push by one or two engineers, because nothing else matters while primary buttons don't work.

Phase One · ~2 weeks

Make it trustworthy

Every tap lands. Every screen exits. Every approval is informed.
  • R01–R03 Reachability: scan CTA, recommendations, Settings rows
  • R04–R05 Wayfinding: universal back, quiz exit
  • R06 Decision render contract + Approve gating
  • R09–R12 Companion intent, item rows, overlay leak, silent scan finish
  • R07 Overlay AX hiding (ships with the overlay fix)
  • Exit criteria: tap-through test of all 26 entry points passes; zero dead chevrons
Phase Two · ~3 weeks

Make it whole

Content integrity, conversation, and the system speaking with one voice.
  • R15–R17 Image failure states, phase formatter, quiz imagery
  • R18–R20 Messaging anatomy + thread identity + decision context
  • R13–R14 Scan exit + visible sync status
  • R23–R24 Project detail substance; token adoption sweep + CI guard
  • R21 Companion & switch accessibility labels
  • Exit criteria: no raw enums or blank rectangles anywhere; messaging readable at a glance
Phase Three · ~3–4 weeks

Make it sing

Dark mode, Dynamic Type, and the platform furniture power users expect.
  • R08 Dark-mode adoption, surface by surface (tokens are ready)
  • R22 Dynamic Type across the typography system
  • R25–R26 Share, search, swipe actions, context menus, Reduce Motion
  • Re-grade against this scorecard; target B+ or better on every row
  • Unlocks next: Aesthete recommendations land in a rail that's no longer empty
07 Appendix

Inventory & capture notes.

What we deliberately credit

The walk experience (whisper bar, haptic milestones at 25/50/75%, idle + tracking-loss recovery, abandoned-scan resume), the empty states ("You're all caught up", "Nothing waiting on you"), the single-sheet-driver architecture in AppCoordinator, 281 accessibility labels, the layered dynamic app icon, and a token system (PatinaColors / Typography / Spacing / Shadows / Gradients) that most teams would envy. The bones are right.

Screen inventory (code audit)

45+ screens: Auth (AuthScreenView, AuthenticationView, QR approval), Onboarding (carousel, camera primer, quiz/result), Consumer (DailyRoom + detail overlays, YourSpaces, RoomProject, RoomSettings, CrossRoom, ManualRoomEntry, Collections, Recommendations, ProductDetail, ARPlacement, Profile), Scan (threshold, walk, review + 3 sheets, saved, soft landing, style conversation, floor plan), Designer (DesignerHome, ProjectList/Detail, DecisionList/Detail, ReceiveDelivery, Consultation), Messaging (ThreadList/Detail), Notifications, Settings/Account, and the Companion overlay.

Not captured on device, and why

Auth & onboarding — capturing would have required signing out the only session on the device with the Account screen unreachable (R03); reviewed from source. Scan review & AR placement — require a physical LiDAR walk of a real room; the phone was stationary during review. Recommendations grid — unreachable via touch (R02); the Aesthete engine behind it is also still a placeholder (AestheteEngineService.swift). These should be re-shot in the Phase-1 verification pass.

Session side-effects

Reviewing on the live account created one junk room ("Kitchen", via the silent empty-scan finish — itself finding R12) alongside the pre-existing "New room" test entries. Recommend cleaning these up when verifying R12.

Evidence

24 captures in screenshots/, numbered 01–24 and referenced throughout. Accessibility-tree excerpts quoted in findings were read live from the running app via the device's AX API.

Implementation status — June 10, 2026

All 26 recommendations were implemented the same day in four waves on main: Wave 0 949d48da (PatinaAsyncImage, PhaseDisplay, dynamic tokens, interim light guard) · Wave 1 4c12efc8 (R01–R07, R09, R11, R20–R21: every P0 — tappable pills, navigation chrome + edge swipe, quiz exit, Settings/Account fix, decision render contract) · Wave 2 15e69a71 (R10, R12–R19, R23, R25: scan gating, messaging anatomy, item rows, share, phase vocabulary, project detail, quiz copy) · Wave 3 e8a77e92 + 1d854e69 (R08, R22, R24, R26: ~620 colors to semantic dark-mode roles + Appearance picker, ~130 fonts tokenized for Dynamic Type, spacing/radius sweep, search/swipe/context-menu/refresh patterns, ~35 Reduce Motion gates, ratcheting token-check script). Two review attributions were corrected during implementation: the "dark services sheet" was the app's lone correctly-dynamic surface (the rest were hardcoded light), and the "Kitchen" room predated the scan — empty scans never created rooms, they abandoned silently, which the new gate + Leave Scan flow now make explicit.
