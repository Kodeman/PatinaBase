Section 04 / 15
Seven places the build wins

Where the shipped thing beats the proposal.

As proposed

Every price is a delta

Base price plus additive adjustments per selected value. I listed “additive deltas are sometimes wrong” as my own risk #2, and mitigated it with a nullable trade delta and a fallback.

product_option_values.price_delta_cents
As built

A sellable variant is its own row, with its own absolute price

Code, SKU, vendor SKU, status, absolute retail and trade prices, lead time, dimensions, weight, a default flag with a partial unique index — alongside the delta path, not instead of it.

product_variantsproduct_variant_valuesconfiguration_pricing_strategy
Built deeperThis is the middle path I missed. It solves my risk #2 better than my own mitigation did, and it still refuses the SKU matrix.
02 · Rules

“Walnut isn't offered with whitewash”

Six rule kinds — compatibility, requirement, exclusion, pricing, lead time, dimension — over a condition/effect grammar, resolved by a rules engine of roughly 366 lines. I deferred validation entirely. This is a real designer problem and they shipped it.

03 · Evaluation

Two-tier pricing truth

An optimistic client-side estimate for feel, then an authoritative evaluate_product_configuration confirm before anything can be placed. Stronger than my additive recompute, and it makes staleness visible instead of invisible.

04 · Integrity

SHA-256 all the way down

Snapshot hashes, immutability triggers, versioned configurations with supersession, an append-only commission event log. Deeper than anything I specified.

05 · RFQ

The quote request carries the spec

vendor_quote_requests gains configuration snapshot columns and a draft-dedupe index. Absent from my plan entirely.

06 · Access

Read-only tables, writes through the front door

All 12 tables carry SELECT-only policies; every write goes through a SECURITY DEFINER RPC. Audience redaction is covered by tests.

07 · Commission

My phase 4, shipped now

Revision ledger, eight-status state machine with timestamp coherence, and a post-issue fulfillment truth: submittal → receiving → installed, evidence-gated and sequential.

The honest summary

On the engine itself, the build is the better document. Where the two plans disagree about depth, the build is right and the proposal was conservative.

Gap 01 06 / 15
The one that matters most

The PO still doesn't say Walnut.

The build enforces snapshot integrity at the exact moment a configuration meets a purchase order — and then prints a document that carries none of it.

As proposed

The line item carries its own spec

A snapshot column on the PO line, rendered into the printed order. It was my number-one payoff, and it works with zero axes ever authored — free text alone would have filled it.

As built

Integrity enforced, paper unchanged

A trigger fires the moment a spec line is linked to a purchase order. It requires the configuration to be approved or issued, re-verifies validity and completeness, recomputes the hash, checks the pricing still matches, recomputes the PO total — and raises on any divergence.

The PDF route was not touched. purchase_orders took no schema change; the route has zero configuration, spec, or option references, and never joins project_ffe_specs.

Gap 03 08 / 15
The missing class

Zero occurrences of COM.

Customer's own material was the third class in my spectrum and the studio principal's first request. It does not appear in the schema, in the workspace, or in the editor — anywhere.

The only trace, in the workspace notes field placeholder="COM or install notes"

A placeholder in a free-text box is exactly the workaround the discovery catalogued: yardage, railroading, the client's own fabric and its lead time, all living in a notes field where nothing downstream can read them. The build reproduced the workaround rather than replacing it.

What's absent

No COM fields anywhere

No COM flag on option groups, no COM requirements on values, no COM details on a configuration. A piece sold at Grade C with the client's own linen cannot be priced, validated, or specified by the engine — only described.

This also means the rules engine, which can express “walnut excludes whitewash,” cannot express “this frame requires 14 yards, railroaded.”

As proposed

Structured fields replace the free-text ones

Axes map one-to-one onto the existing spec fields. Dimensions come from the selected value. The old flat facets get deprecated as the structure fills in behind them.

As built

The seam is half-crossed

Placement does denormalize material and finish back into the flat fields — the good half. But selected_dimensions is still a raw JSON textarea, and the old flat facets (colour chips, a singular finish) remain editable on the very same page as the new editor, un-deprecated.

GapTwo places to say what colour the chair is, on one screen, with no rule about which wins.
Gap 04 09 / 15
The old scaffold

There are now two variant systems.

My proposal asked for one deletion before anything new landed: the dead e-commerce scaffold. It wasn't deleted, so the new work landed beside it.

As proposed

Remove the Variant and CustomizationOption types and the admin variant editor. Stop writing the flattened facet arrays. One vocabulary for variance, and it's the new one.

As built

The admin variant editor is still mounted and still pointed at a NestJS service. The old Variant type still sits in product.ts. Next to them, a new 504-line type module with 43 exports, including ProductVariantDefinition, and a real product_variants table.

Divergence 10 / 15
Not a gap — a genuine disagreement

Decide later, or don't decide at all.

As proposed

Warn, never block

Every axis is skippable. “Decide later” is a real answer that a designer standing in a client's living room can give, and it becomes visible readiness debt rather than an error. The system nags; it does not refuse.

As built

Approval-gated

Placing a custom piece requires an approved configuration, an approved revision, and both designer and client approvals. Linking a spec to a PO raises if the configuration is unapproved, stale, or a cent off. The commission footer is a real state machine.

DivergenceTheir integrity is stronger than mine. The risk is what a designer does when the gate is closed.

The escape hatch is accidental but real: every legacy path is still fully open. A designer who hits the approval gate can back out, use the picker, and place the same piece with no configuration at all — no warning, no debt recorded, no trace that a decision was skipped. The strictest gate in the system sits on the path that is easiest to avoid.

The reconciliation

Keep the gate. It's the right call for money and paper. Add the soft path in front of it: let the picker record an incomplete configuration as debt, so the choice a designer defers is captured rather than lost. Strict at the PO, forgiving at the sofa.

“Never silently alter an approved selection, an issued book, a sent RFQ, or a confirmed PO.”

Process 11 / 15
Stated plainly, not as blame

What a reviewer can and can't confirm.

These are the seams a second pair of eyes finds in a nine-commit day. Most are hours of work, not days — but they're the difference between “built” and “landed.”

Ledger

The migration ledger stops at 00382

Objects from 00383 through 00403 exist anyway — applied out of band via psql, which is a pre-existing pattern here rather than something new. The consequence is real: supabase migration list and db push can't be trusted, and whether 00403 is applied in production can't be determined from the repository. That two email migrations were renumbered past a spec-book collision confirms a numbering collision already happened.

Tests

A ~940-line SQL suite that nothing runs

pgTAP-style, executed by hand via psql, registered in no runner. Thirteen TypeScript test files do real work — nine workspace cases across the bed, sectional and table archetypes, drift repair, revision, plus a 118-line spec-book redaction test. There is no end-to-end walk of any archetype.

Data

Every new table is empty locally

No seeds. Nobody has configured a real piece yet, which means the first person to meet this engine will also be the first to find out how it feels.

Rollout

No feature flag anywhere

The house convention is PostHog gating. This ships unconditionally to every designer, before validation. Six analytics events are defined; three have confirmed call sites.

Loose ends

Dead exports and an interim shim

useApproveProductConfiguration is exported with no consumer; an onResolutionChange prop is unused. The order assistant carries an explicit dual-shape comment: it accepts both shapes “while the Supabase hook migration rolls out.” Zero TODOs in the whole change — the loose ends are in the shape of the code, not in comments.

Visibility

The client approves what they can't see

A commission records “Record both approvals” via a button the designer presses, while the published spec book redacts configuration from the client audience entirely. The client portal has zero awareness of any of this. That's defensible as a first cut; it needs a stated ruling rather than an accident.

The one failure with two authors

Both plans asked for designers. Neither went and got them.

The product review

Five to eight sessions before schema lock

Its closing sections recommended designer sessions before the schema hardened, under the heading “Recruit now.” The document itself says validation “is part of the proposed next step” and names its research honestly: Programa, Schema.org, OFML, Roomle, Configura — desk work, not interviews.

The schema landed two and a half hours later.

The variance proposal

An unmitigable risk, clearly labelled

My discovery was synthesized composites, not real designers. I put that on its own slide and called it the risk I couldn't mitigate. Then I shipped 22 slides of schema recommendations anyway.

Naming a gap is not closing one.

Shared missTwo documents, one omission, no asymmetry worth arguing about.
The correction

One session with Leah, before this reaches every designer. Put a real project in front of the piece workspace, configure a bed, a sectional and a commission, and watch where she stops. Two hours buys back the only thing neither plan could buy for itself — and it's cheaper now, before the first configuration exists, than it will ever be again.

What to watch for in that session

Does she reach for the picker or the piece room? Does she try to type COM into the notes field? Does she skip an option group and expect the system to let her? Does she understand the difference between an estimated price and a confirmed one? Four questions, four schema decisions.

Reconciliation 14 / 15
What to do about it

Ten items, in the order they pay.

P0 · before designers meet it

Finish the chain, open the door

  1. The PO says Walnut. Join project_ffe_specs in the generate route and render a spec block. One route. Completes the promise the link trigger already enforces.
  2. Route the picker. Send optioned and configured pieces from the picker into the configuration flow, or embed the pane. Closes the bypass and retires the second placement path.
  3. Decide the rollout. A flag and a posture, plus the designer session both plans asked for — before this is in front of everyone.
Each of these is small. Together they turn an engine into a feature.
P1 · the next pass

Close the classes, clear the ground

  1. COM and COL. Either an option-value kind or COM details on the configuration — whichever the Leah session says.
  2. Delete the old scaffold. The admin variant editor and the old Variant type. One vocabulary.
  3. Bridge decisions. Derive sibling decision cards from an option group so a client can meet a real choice.
  4. Make the tests run. Register the SQL suite in a runner, reconcile the migration ledger, and walk bed, sectional and commission end to end.
Item 7 is the one that lets anyone else touch this code safely.
P2 · when it earns it

Feed it, and finish the seam

  1. Capture feeds the groups. Stop the extension flattening scraped variant lists; land them as suggested groups for a human to confirm.
  2. A real dimensions editor, and deprecate the flat facets sitting beside the new ones.
  3. A client-visibility ruling. Decide what a client sees before they're asked to approve it.
None of these block the pilot. All of them are cheaper decided than discovered.

Green-light the P0 trio and book the session.

The hard part is done and it's better than what I proposed. What's left is short, and all of it is between the engine and the people who have to use it.
