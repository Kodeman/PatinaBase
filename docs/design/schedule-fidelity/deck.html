The anchor holds.

The schedule spine can be the document’s single status organ — but only if it knows how hard its own dates are. An engagement begins as a season and ends as a Tuesday. Today the doc renders both in the same typeface and asks the designer to guess which is which, so it renders Active · Week 2 above NO ACTIVE OR DELAYED PHASE IS CONFIGURED and neither line can be believed. This deck proposes one model — three fidelities, hardened by commitment events, never by asking anyone to set a date.

What this is
A unification and wiring design over machinery that is already built and ratified (R99–R105, behind schedule-spine). Not a rebuild.
What it asks for
Eight rulings, one genuinely new act (install booking), one narrow schema addition argued as unavoidable, and one dead field deleted.
What it does not ask for
A second time surface, a chain backfill, a client-facing ledger, or a prompt that says “please enter a date.”
Grounded in
Verified code, schema and decision lineage — grounding.md. Every mechanism named below exists unless explicitly flagged NEW.
02

The dilemma

Four truths, no arbiter

On Winkys winktastic loft — the best-populated live project in the studio — four independent pieces of code answer the question “where is this job?” None of them consult each other, and only one of them is right.

VoiceWhere it livesWhat it computes fromWhat it says on Winkys

The resolver packages/utils/src/schedule.ts durations, links, anchors — the one pure computation of time a fully resolved six-phase chain, Consultation → Care — read by nobody outside the flag

Why it happened

Not because four teams disagreed. Because the system has exactly one way to say “when” — a date column — and a date column cannot say how firmly. When an engagement is born, a designer’s honest answer is “late summer into winter.” The only place to put that answer is projects.start_date / target_end_date, which look exactly like the install date the client has taken a day off work for. From that moment on, every consumer downstream is free to do arithmetic on a guess. Week 2 is that arithmetic.

So the four voices are not four bugs. They are four attempts to answer a question the data model refused to hold: how hard is this date? Direction A adds that one missing dimension and then makes every voice read it.

The corollary Kody has already ruled on. The cure is not a better prompt. Nobody wants a modal asking them to firm up procurement. Firmness must be a by-product of acts the studio already performs — a signature, an executed authorization, a released purchase order, a booked install week. The schedule hardens because the business hardened, not because someone was nagged.

03

The model

The fidelity ladder

Three tiers. Every one of them already has machinery behind it. The ladder is a reading of the resolver’s existing source field — not a new column, not a new state machine.

Band

Lead → proposal

Only projects.start_date and target_end_date exist. The spine renders one soft span with no interior edges — not six phases with fake boundaries. The header states a season, never a week: TARGETING SEP – FEB. No phase inside a band may display a date, because no phase inside a band has one; the resolver reports source: 'unresolved' or 'legacy-dates' and the band is the honest rendering of both.

Kills: Active · Week 2 on an engagement with no chain. Week counting is arithmetic on an anchor; a band has no anchor, so there is no Week N to count.

Frame

Agreement executed →

Signature is already the moment the system cuts baseline revision v1 inside activate_proposal_as_project. That same moment gives the chain its first real anchor: the engagement start. Phases now lay out as duration_days off that anchor through follows_phase_id — the resolver’s forward pass, already written.

Frames render as dashed ranges, never dates: Procurement · ~6 wks · mid-July frame. The vocabulary is deliberately imprecise because the computation is: a frame is a consequence of durations, and durations are estimates until something commits them.

Uses: the resolver’s source: 'chain'. Adds: nothing. The chain is built; only the rendering vocabulary is new.

Committed

Per phase · event-driven

A phase hardens one at a time, when its own commitment event fires. Executed furnishings authorization hardens the procurement thread. A released purchase order informs lead time. A booked install week hardens install. close_project is the final hardening and already refuses to fire on an unfinished schedule.

Hardening is an anchor_date write, made through the existing ripple → commit_schedule_edit → cut_schedule_revision path — R100’s requirement, satisfied without a new write path. Committed bars are drawn solid with end ticks: they are the only bars in the system you can hang weight from, and the only ones a client is ever shown (R101).

Crucially per-phase. A project is almost never “committed.” It is a band that grew a frame that grew, phase by phase, a spine of hard weeks. All three fidelities coexist on one spine at once — and that mixed picture is the normal, correct state.

The honesty rule

No surface may render a date firmer than the resolver’s source supports. Week N requires an anchor upstream of it. A range requires a chain. Everything else is a band. A band is a legitimate state of an engagement, not an error the designer caused — so it is never rendered in the machine register that produced NO ACTIVE OR DELAYED PHASE IS CONFIGURED.

The line: ceremonies harden, facts propose

I56 ratified that chain adoption is “assisted, confirmed, never silent.” Kody has ruled that hardening must not come from asking anyone for a date. These are only in tension if you assume the confirmation has to be a separate act. It does not — it has to be a real act by a human who understood what they were doing. That test splits the events cleanly in two.

Ceremonies harden directly

A ceremony is R2’s six-part boundary — ARTIFACT, QUESTION, SCOPE, IMPACT, AUTHORITY, CONFIRMATION. The confirmation already happened, deliberately, with the impact stated on the face of it. Nothing is silent: the schedule consequence is written into the IMPACT line the person read before they confirmed. Executing an authorization that says “procurement starts the week of 8 Dec and install holds at 26 Jan” is confirming that schedule.

The corollary is a hard constraint, not a nicety: a ceremony that cannot state its schedule impact before confirmation is not permitted to harden anything. If the IMPACT line can’t render it, the ceremony downgrades to a proposal.

Operational facts only propose

sent_at on a purchase order is a fact about a message, not a promise about a week. It arrives from a background job, from a vendor’s reply, from a webhook. Nobody stood in front of an IMPACT line. So it never writes: it prepares a ripple — the existing single in-flight RippleProvider preview — which the designer commits in one act, or dismisses.

This is the same confirm strip that already exists for manual edits. Operational hardening adds no new interaction grammar; it adds a new author of the pending diff.

Where I diverge from the brief

The two-way split is right but incomplete. It answers “what may write” and leaves “what may overwrite” undefined — and that is where a system like this does its real damage. I propose a third class:

Contradictions never propose — they report. When an operational fact disagrees with an already-committed anchor (a delivery slips past a booked install week), it does not prepare a ripple that would move the anchor. It raises a conflict, per R4: one fact, exactly three renderings — the terracotta stamp on the spine, the guide sentence, the desk re-sort. Re-committing is a human act with a name. A prepared ripple that silently offers to move a date the client is holding would be exactly the silence I56 forbade, wearing a confirm button.

Alternative considered — and rejected

Uniform proposal: every event, ceremonies included, prepares a ripple the designer commits. Cleaner as a rule, and tempting. Rejected because it makes the studio confirm the same decision twice — once inside the ceremony, once in a schedule strip minutes later — which trains people to commit ripples without reading them. That is worse than silence: it manufactures consent. It also breaks the client-facing case, where the anchor must be true the instant the ceremony completes, not whenever the designer next opens the doc.

05

Ripple semantics

When a delay meets an anchor

This is the scheduling dilemma, and the answer is already in the resolver. A delay is not a single behaviour. It behaves one way in soft material and another way against something committed — and the difference between those two behaviours is the entire value of knowing your own fidelity.

Through frames — it flows

Unanchored downstream phases shift automatically on the resolver’s forward pass. Nothing is asked of anyone. The frame was always an estimate; a later estimate is still an estimate. The spine simply redraws and the ledger records it.

Into an anchor — it stops

The anchor does not move. The resolver reports shrinking slackDays, then chain_does_not_fit with overrunDays. R100 already says it: a change that would break an anchor names the conflict instead. The UI draws the collision; a human decides.

Overdue is the same fact. A phase running past its committed end is not a new condition needing new chrome — it is R4’s overdue condition sourced from the resolver instead of from a stored column, and R8 keeps it studio-side.

Reconciling the classifier

R1 already narrowed the workflow classifier to section sub-labels and track fills. But narrowing its output did not remove its ability to disagree, because it still performs its own selection: it scans phase rows for an active-or-delayed one and, finding none, announces NO ACTIVE OR DELAYED PHASE IS CONFIGURED over a perfectly good six-phase chain. Two components each picking “the current phase” from the same rows by different rules will disagree eventually; that is a structural property, not a bug to patch.

The split: the resolver selects, the classifier names. The resolver alone answers which phase is current and how firm it is — it is the only code that understands anchors, links and time. The classifier receives that phase and answers which canonical stage it belongs to, a taxonomy question with no time in it. The sub-label is then a composition of three parts from two components that cannot contradict each other, because only one of them ever chose:

stage (classifier)  ·  position (resolver)  ·  fidelity (resolver)

“Documentation · week 2 of ~5 · frame”
“Procurement · starts 8 Dec · committed”
“Not yet composed · targeting Sep – Feb · band”

When the resolver hands over nothing, the answer is not an error — it is the band, and the sub-label says so in the designer’s language. Two of the review’s leaked-machinery strings die of this change alone: NO ACTIVE OR DELAYED PHASE IS CONFIGURED and 2 ACTIVE PHASES NOT CLASSIFIED TO A CANONICAL STAGE — the latter because an unclassifiable phase now degrades to naming itself rather than to reporting a taxonomy failure.

07

Tension 2 — the one new mechanism

The install window

Everything else in this deck is wiring. This is not. There is no table, no RPC and no act anywhere in the system that books an install — and install week is the single most committed date in an engagement, the one the household takes a day off work for.

Today the closest thing available is a designer typing a date into the entry grammar, which auto-anchors. That works mechanically and fails completely as a record: it captures a date and loses everything that makes the date binding — who agreed to it, when, on what understanding, with what access arrangements. A booked week that only one party remembers agreeing to is not a commitment; it is a note.

The act

The install window is an R2 boundary ceremony — the same six parts as every other gate, reusing the grammar rather than inventing a third one. Per the §7 guard it is written in actor-neutral language: it names the site and the window, never a commercial actor, until №7 resolves.

PartThe install window ceremony
ArtifactThe window itself — a start date, a working span in days, and the site it applies to.
QuestionIs the site held for these days?
ScopeWhich rooms, and which authorized waves must have landed by then.
ImpactInstall anchors to the window. Procurement and delivery become backward-computed against it — the resolver’s backward pass, already written. Slack upstream is stated in days, out loud.
AuthorityWho holds the site for that week, and what access the window depends on.
ConfirmationHolding the window cuts a revision. Releasing it later is a second, equally named act — never an edit.

The schema question — flagged for ruling

R7 set the precedent hard: derive over existing columns, zero new schema. I tested three ways to honour it and recommend the third.

Option A — zero schema

The window is just anchor_date on the install phase plus a revision-ledger note. Rejected. The ledger records that a date changed and who committed it, not that a site was held, by whom, under what access. The evidence of the commitment lives nowhere, which is precisely the failure the ceremony exists to fix — and it gives the “re-book the window” branch of Mock C nothing to re-book.

Option B — overload site_requests (00374)

It already carries a due_at and points at a site. Rejected. It is a Field media-capture instrument; a request to photograph a room and a commitment to occupy it for a week are different kinds of fact with different lifecycles and different audiences. I56 A0.3 already refused exactly this move for payment milestones versus schedule milestones, on the same grounds. Overloading it buys one table and costs the meaning of two.

Option C — recommended: one narrow table

install_windows — project, phase, window_start, span_days, state (proposed | held | released | fulfilled), held_at, held_by (server-resolved, like every other ledger actor), access_note. That is the whole surface.

Why this survives R7: R7 forbids duplicating a fact that already exists. The install date is not duplicated — it stays where every other date lives, as anchor_date on the install phase, written through commit_schedule_edit like everything else. What the new table holds is the evidence of the commitment, which exists nowhere today. One table, one RPC to hold a window, one to release it, both cutting revisions. It is also the natural seat for the install-mode composition the review deck asks for in T2 — a week has a shape, and this is where that shape would hang — though that is a separate design and not requested here.

This is the deck’s only schema request and the only place it asks for a new mechanism rather than a new wire. Everything else — every other hardening event in §04 — runs on acts that already exist and columns that already exist.

08

Tension 4 — and the docket

What this asks of the system

Path to ship

Sequenced by risk, not by dependency. The governing hazard is that two date-computation paths are live in production right now — the legacy stored cascade that everything outside the flag reads, and the pure resolver behind it — and the collapse in §06 is what finally retires one of them. Nothing below reaches production before the flag state itself is honest.

  1. Clear the ground. Reconcile the schedule-spine flag contradiction (I55: live at 100% on PostHog against a design-authority-only intent) and land the comember-widening pass owed by R105. Neither is optional; the collapse makes the flag load-bearing for every project surface, not just the spine slice. Fix the dead target_completion field here too — it is one line and it is wrong today regardless of anything else in this deck.
  2. Teach the resolver to speak fidelity. Derive the three tiers from the existing source field and expose a small vocabulary — tier, position phrase, fidelity phrase — from the one impure door, useResolvedSchedule. Pure addition, no consumer changes, nothing user-visible.
  3. Collapse the mouths. Header vitals, week-N derivation, stage sub-label, desk motion chip — all four re-derive from that vocabulary. This is the change that kills T1, and it can ship before a single hardening event is wired, because a band honestly rendered is already better than a fabricated week.
  4. Wire the ceremonies. Signature first (its anchor already exists implicitly — v1 is cut there today), then furnishings authorization, then trade scope, then close. Each is an IMPACT-line addition plus one call into the existing commit path. Ship them one at a time; each is independently valuable and independently reversible.
  5. Wire the operational proposals. PO release and delivery prepare ripples. Last, because this is where the prepared-diff volume lives and it wants real usage data to tune.
  6. The install window — after its ruling. Schema, two RPCs, one ceremony face. It is the only step gated on a decision rather than on the step before it.

The one-way door. Step 3 makes the resolver load-bearing for surfaces that currently render for every project in the studio, flag or no flag. If the flag stays contradictory, step 3 either ships to everyone unintentionally or ships to nobody while looking shipped. Step 1 is not housekeeping; it is the gate.

Legacy stored dates do not get deleted by this deck. They stay as the resolver’s last-resort source: 'legacy-dates' — which renders as a band, which is honest, and which is why no backfill is needed and I56’s no-backfill rule stays intact.

Decisions requested

Numbered in the house sequence, continuing from R106.

  1. R107 The fidelity ladder is the schedule’s vocabulary. Band, Frame, Committed — derived from the resolver’s existing source, per phase, not per project. All three may coexist on one spine. No new column.
  2. R108 The honesty rule: no surface renders a date firmer than its source supports. Week N requires an anchor upstream of it. Header vitals, week-N derivation, stage sub-label and desk motion chip all re-derive from the resolver and render its output verbatim. This is the T1 fix and the reason to elect the spine as the status organ.
  3. R109 Ceremonies harden; operational facts propose; contradictions report. A ceremony writes an anchor directly because its IMPACT line stated the schedule consequence before confirmation — satisfying I56’s never-silent posture inside the act rather than after it. An operational fact prepares a ripple the designer commits in one act. A fact that contradicts a committed anchor never proposes moving it; it raises an R4 conflict. The third clause is this deck’s addition to the orchestrator’s two-way split.
  4. R110 A ceremony that cannot state its schedule impact may not harden. Hardening is scoped by the ceremony’s own SCOPE part and disclosed in its IMPACT part. If the impact cannot be rendered before confirmation, the ceremony downgrades to a proposal. This keeps R2’s six-part anatomy the sole gate grammar.
  5. R111 The resolver selects the phase; the classifier names its stage. The workflow classifier loses its independent selection of “the active phase” and receives the resolver’s. Sub-label = stage · position · fidelity. Disagreement becomes structurally impossible rather than merely unlikely. R1-compatible; narrows R1 further rather than reopening it.
  6. R112 The install window is a boundary ceremony with its own record. One narrow table install_windows plus hold and release RPCs; the date itself stays as anchor_date written through commit_schedule_edit. Actor-neutral copy per the §7 guard. The only schema this deck requests, argued against zero-schema and against overloading site_requests in §07.
  7. R113 An unanchored engagement is a legitimate state, not a setup error. A band renders as a band, in the designer’s language, on the spine, the header and the desk. Machine-state strings about classification and provenance leave the reading surface. Answers T6 for the schedule surfaces specifically.
  8. R114 Flag reconciliation and comember widening gate the collapse. I55 and R105 are cleared before any surface in §06 re-derives. Legacy stored dates are retained, not backfilled, and render as bands via source: 'legacy-dates' — preserving I56.
  9. O10 Open — what fidelity does a client see? R101 keeps the spine studio-only and proposals carry anchored milestones only, so the safe default is that clients see committed anchors and nothing else — no bands, no frames, no ledger. But the install window ceremony has an actor on the other side of it who must be told a week. Depends on O8. Flagged, not answered here.
  10. O11 Open — do payment milestones ever harden a phase? Deliberately deferred. project_payment_milestones was kept semantically separate from schedule_milestones by I56 A0.3, and this deck does not reopen that. Named so it is a decision rather than an omission.
