The thesis, and three things to do this week.

Patina's product surface has outgrown its boundaries: the auth layer trusts unverified tokens, three portals re-implement the same hooks, and four backend stacks share unclear ownership — none of which require a rewrite, but all of which require deciding what the seams are before the next feature. The fix is mostly subtraction, not addition.

06 / 13

Auth security.

Anyone with a valid-shaped JWT can claim to be admin. Four findings, ~1 week total to fix.

A1

JWT signatures are not verified

The guard splits the token, base64-decodes the middle segment, and trusts the JSON. SUPABASE_JWT_SECRET is never consulted.

const payload = JSON.parse(
  Buffer.from(payloadPart, 'base64url').toString('utf-8')
);
// No signature verification.
if (payload.exp && payload.exp * 1000 < Date.now()) return false;
packages/auth/src/index.ts:79-91
A2

Dev fallback synthesizes a privileged user

If the env var is unset, every unauthenticated request is treated as a logged-in user — exactly the misconfiguration that occurs silently after a Coolify env-panel edit.

if (!process.env.SUPABASE_JWT_SECRET) {
  request.user = {
    sub: 'dev-user',
    email: 'dev@patina.com',
    role: 'authenticated'
  };
  return true;
}
packages/auth/src/index.ts:69-74
A3

Silent default-role fallback per portal

If app_metadata.roles is missing, the portal silently grants its namesake role. A new account landing on admin.patina.cloud is admin.

const roles = (user.app_metadata?.roles as string[]) ||
              (user.user_metadata?.roles as string[]) ||
              ['admin'];  // ← per portal: admin / designer / client
apps/{admin,designer,client}-portal/src/hooks/use-auth.ts
A4

PermissionsGuard is a stub

Every controller that uses @RequirePermissions(...) is decoratively guarded but the guard does nothing. The decorator is theatrical.

@Injectable()
export class PermissionsGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    return true;
  }
}

Ship discipline.

CI runs but doesn't gate. Coolify deploys silently land stale. Eight compose files with no documented hierarchy. ~1 week to fix.

D1

No CI gates

.github/workflows/docker-publish.yml builds images on push, but no workflow blocks merges on lint / typecheck / test / build. Main can be broken at any time.

→ Add pr-checks.yml; require as status check on main · 1 day
D2

Coolify doesn't force-pull

Memory note (verified): /restart + /deploy skip image pull. Deploys silently run stale images. The reliable path is SSH + docker compose pull && up --force-recreate.

→ Pin to image digests, or force-pull in deploy.sh · 1 day
D3

Eight docker-compose files

Across /, /infra/, /infra/coolify/, /services/*. Two (infra/docker-compose.deploy.yml, infra/docker-compose.frontend.yml) smell stale.

→ Canonical compose in infra/coolify/; infra/README.md mapping · 2 days
D4

Hardcoded IP + stale env detritus

infra/deploy.sh:27 falls back to 192.168.1.14. infra/.env.swp dates to March; .env.bak-* files have no rotation policy.

→ Require PATINA_PROD_SSH; delete the stale files · 1 hour

NOT a problem   Secrets are properly gitignored — .env and secrets.txt exist on disk but never tracked. (An explore agent got this wrong; correcting the record.)

The four-stack backend.

Four backend stacks share unclear ownership. The middleware layer is 9,338 lines — an API gateway for a product with three services.

The proposed rubric

USE A SUPABASE EDGE FUNCTION WHEN: · trigger is a Supabase event (db trigger, auth webhook, storage) · stateless and completes in < 5s · no @patina/* package imports needed USE A NESTJS SERVICE ENDPOINT WHEN: · trigger is an HTTP request from portal or external client · stateful, long-running, or composes multiple services · code reuses @patina/types, @patina/cache, domain models CURRENTLY COLLIDING (decide a side): · automation-processor · decision-reminders · campaign-dispatcher

12 / 13

What this does not require.

Recommendations carry their own cost. Some plausible moves were considered and rejected.

  • No rewrite. Problems are local. Auth is broken in 4 specific files; portal scaffolding is duplicated in 3 specific patterns. A rewrite trades fixable problems for unknown ones.
  • No framework migration. Next.js 15 + React 19 + NestJS + Supabase is a fine stack for this product. Switching anything introduces months of churn for marginal gain.
  • No Supabase replacement. Self-hosted Supabase on Coolify is unusual but works, and the team has institutional knowledge of its quirks. Migrating to Neon + Clerk + S3 would cost a quarter and change nothing about application code.
  • No microservices split. The 3 NestJS services already exist; the question is whether to consolidate them, not split them further.
  • No "harden aesthete-engine now." Experimental, per status. Investing in OpenAPI contracts is premature until the ML hypothesis validates.
  • No new tooling category. No new observability stack, no new package manager, no new build tool. Infra is sufficient; configuration is the gap.
