Capture, end to end.

Every screen, state, and function of the browser extension — from install to a saved, verified record — mapped as one connected flow. This is the build-facing spec: what each screen does, how the controls behave, where it leads, and how it fails gracefully.

How to read this · No. 01

A shared vocabulary first.

The flow map and screen specs use a consistent set of node types and state colours. Colour carries meaning throughout — the same patina logic as the product: verdigris is value & success, brass is a decision or expertise, rust is friction or an edge.

Entry point

How the user arrives — toolbar, shortcut, context menu, or install.

Screen state

A distinct view of the panel the user can see and act on.

Decision

A branch — the flow forks on page type, data quality, or user choice.

Success / terminal

A capture reaches the library or another resolved end state.

Edge / fallback

Blocked sites, missing data, errors, and offline — handled, never dead-ended.

Anatomyreference
The capture panel, labelled

Most of the extension is this one panel in different states. Four regions repeat across nearly every screen:

  • A · RecordExtracted fields with verification badges — verified, needs-check, or not-found.
  • B · Trade layerTrade pricing and availability in brass — the expertise the consumer web hides.

Every panel state shares a header (◆ Capture · settings · close) and a connection strip showing the active workspace and save destination.
